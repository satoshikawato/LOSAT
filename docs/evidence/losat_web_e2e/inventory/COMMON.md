## What to produce
For your range, enumerate every NCBI function (and every branch of it that the in-scope options or inputs select) that executes on that path and can change output bytes, warnings, errors or exit status, follow the calls from the entry points named in your range part (include static helpers and macros with logic), find LOSAT's counterpart, read both, and classify each row:

- `faithful`: LOSAT has the same logic and the same C details for this branch: integer widths and wraparound (Int2/Int4/Uint4/Int8/size_t), float types (float vs double) and rounding, float-to-int conversions, sort order and tie-breaks (glibc `qsort` is a stable merge sort), call order and timing, message text and exit code. An implementation that differs only for speed but provably gives the same output is `faithful` with note `equivalent: <how>`.
- `divergent`: LOSAT has code for it but some logic, value, message, exit code or C detail differs. Say exactly what differs and give an input that shows it (ideally one you ran on both binaries; name the scratch files).
- `unported`: no LOSAT counterpart for this branch and it can change output, warnings, errors or exit status (e.g. LOSAT rejects `-matrix PAM30` today: the NCBI functions that PAM30 reaches are `unported`, and the row notes the LOSAT rejection). Use `unported` (not `rejected`) for everything LOSAT currently rejects with a generic or ad-hoc error, so the session sees the whole porting job.
- `rejected`: LOSAT stops with an explicit error naming the option or value as not supported by LOSAT, and there is a reason to keep it rejected (an NCBI crash, a later session). Cite the LOSAT check.
- `exception`: an approved exception (above) covers the difference. Cite it.
- `n/a`: executes but cannot affect output, warnings, errors or exit status (allocation, freeing, bookkeeping). Give the reason.

`impact` (how broad the inputs that show a difference are; `none` for faithful/n/a/exception): `high` = default-like options or common inputs; `medium` = a common non-default option value; `low` = rare inputs or extreme values.

`proposal`: `keep` (faithful, n/a, exception), `port:S|M|L` (transpile; S = under ~100 Rust lines, M = a few hundred, L = more, e.g. a data table set or a whole algorithm), or `reject:<reason>` (when porting is not sensible, e.g. NCBI crashes or the branch needs `-db`). Prefer `port` whenever NCBI's behaviour is deterministic and reachable with in-scope options.

## TSV format (tab-separated, one header line, then one line per row)
`range	row	ncbi_file	ncbi_lines	ncbi_function	branch	losat_location	status_before	impact	proposal	evidence	notes`
- `row`: 1, 2, ... within your range.
- `ncbi_file` relative to `c++/` (e.g. `src/algo/blast/core/blast_stat.c`); `ncbi_lines` `start-end` of the function or branch.
- `branch`: which program(s) and which option/value or input condition, prefixed with the program(s): `P:` blastp, `N:` tblastn, `X:` tblastx, e.g. `PN: -matrix PAM30 (gapped)`, `X: -window_size 0`. Use one row per program when LOSAT's counterpart differs per program.
- `losat_location`: `path:line(function)` relative to `LOSAT/src`, `;`-separated if several, `-` if none.
- `evidence`: scratch file names of oracle/LOSAT runs that show the behaviour, or `source` if read only.
- `notes`: one line, concrete: what NCBI does (values, message text, exit code), what LOSAT does, and for divergent/unported the exact difference. No tabs or newlines inside a field.

Also write `<RANGE>_notes.md`: the call path you followed (entry points, order), the NCBI tables/data the port needs (where they are, sizes), surprises, and anything the session must decide.

## Working rules (important: usage limits)
- Append each row to the TSV as soon as you have classified it (open, append, close), so partial work survives if you stop. Create the file with the header line if it does not exist. If the file already has rows (you were restarted), continue after them without duplicating.
- Work function by function. Do not spend long on one function: if you cannot decide in reasonable time, write the row with status `divergent` or `unported` and notes starting `UNSURE:` saying what to check.
- Never guess NCBI behaviour; read the NCBI source. When you run an executable to confirm, say so in `evidence`.
- When done, reply with: the number of rows per status, the list of `divergent`, `unported` and `UNSURE` rows (row, function, branch, impact, proposal, one-line difference), and the most important points of your notes.

# LOSAT v0.2.0 certification plan: lineage, certification set, platform claims

Status: plan (2026-10-25, release line RL1). The results are written into `docs/release/v0.2.0.md`
(the GO record) and the run identifiers into `docs/release/v0.2.0_rc_contract.json` when the
candidate is certified. Owner decisions this plan rests on (2026-10-25): scope B' (dev at the cut day
plus the five small completions), cut 2026-11-01 delayed until the always-on switches have graduated,
memory at or below NCBI on every cell of the standard table (n <= 16) is required, no speed regression,
five native platforms and WASI serial certified, WASI threads supported, the Web GUI a preview, the
TBLASTX local-subject genetic-code deviation kept as an approved difference.

## 1. Lineage: what is re-run and what is reused

v0.1.0 certified the integrated runtime at `5845d22ed` (2026-08-31) and four native platforms at
`647e5f13c` / `e9f07039f` (2026-09-02 / 2026-10-14), and its release-candidate assembler reused that
certification only when the candidate differed from the certified commit in no runtime input
(`prepare_release_candidate_v010.py`, `RUNTIME_INPUT_PATHS`). `LOSAT/src` changed in more than 1,400
commits since; the reuse rule correctly refuses every v0.2.0 candidate. The v0.1.0 contract, assembler
and workflow stay as they are (frozen 0.1.0 records); v0.2.0 gets its own three files.

Rules for v0.2.0:

1. **Everything LOSAT-side is re-run on the candidate commit** `C` (the dev commit that is promoted to
   `main` on the cut day and from which `release/0.2` is made). No LOSAT output hash, classification or
   platform result from an earlier commit is carried over as certification evidence. Historical hashes
   stay in the manifests as provenance only.
2. **Reused: NCBI-side records only.** The frozen NCBI BLAST+ 2.17.0 outputs
   (`LOSAT/tests/outfmt0_manifest.tsv`, `db_search_manifest.tsv`, `*_regression`, `range_regression`,
   `fasta_input`, the Gate A manifests) and the NCBI platform characterisation
   `LOSAT/tests/ncbi_platform_variance_v011.json` (PD-NCBI-PLATFORM-VARIANCE) are records of NCBI's
   behaviour and do not depend on LOSAT's commit. The `-subject` fixture rows are nevertheless
   re-executed with the oracle on the certification day (set D below), which turns "frozen" into
   "executed" evidence for every program and task.
3. **The release-candidate commit `R` may differ from `C` only outside the runtime inputs.** After the
   runs, the contract is filled (candidate SHA, run identifiers, evidence hashes) and committed with the
   release documents on `release/0.2`; that commit `R` is the one the RC workflow builds and tags. The
   assembler requires `C` to be an ancestor of `R` and `git diff --quiet C R -- <runtime inputs>` to be
   empty. Runtime inputs of v0.2.0: `LOSAT/src`, `LOSAT/Cargo.toml`, `LOSAT/Cargo.lock`,
   `LOSAT/build.rs`, `LOSAT/.cargo`, `LOSAT/tests` (fixtures, manifests, gate scripts) except the two
   release-tooling files `LOSAT/tests/prepare_release_candidate_v020.py` and its test, and
   `docs/product_decisions`. `README.md`, `LICENSE`, `CHANGELOG.md`, `docs/release`, `changelog.d` and
   the Bioconda recipe may change between `C` and `R` (they go into the archives as documents).
4. A fix found by the certification produces a new candidate `C'`; every run of section 2 is repeated
   on `C'` (the GitHub side is about one working day in wall time, the local side a few hours).
5. Lineage of v0.2.0 towards v0.1.0 is recorded, not relied upon: the contract keeps the v0.1.0
   certified SHAs and the assembler checks that `C` descends from them (provenance of the oracle set).

### 2.1 Threaded Wasm n16 out-of-bounds (GO blocker)

The nightly of 2026-10-25 failed once on a branch run with `memory access out of bounds` in
`__wasi_thread_start_C` (blastx, 16 threads) and passed on rerun; the dev run was green. The Owner
holds GO until the cause is known. Requirement for v0.2.0: the cause is written down (the ci-nightly-dev
line reports it), the fix or the exclusion is in `C`, and set G is green three times in a row on `C`.

## 3. Tasks without a v0.1.0 certification document (dc-megablast, blastn-short, blastp-fast, blastx, tblastn)

v0.1.0 certified blastn (megablast, blastn), blastp and tblastx. For v0.2.0 the other tasks and programs
are certified on the same two legs, without new certification scripts:

- **NCBI executed on Linux x64**: set D re-executes the oracle for every `-subject` row of
  `outfmt0_manifest.tsv` (dc-megablast 34, blastn-short 28, blastp-fast 9, blastx 115, tblastn 177
  rows; outfmt 0, 5, 6, 7, 8, 9, 11-17) and set E re-freezes the `-db` rows (blastx 117, tblastn 103,
  blastn and blastp the rest). The frozen bytes equal to a fresh 2.17.0 run plus LOSAT equal to the
  frozen bytes is the same evidence the Gate A pairs give, on far more rows; the samples are not a
  hand-picked subset but the whole manifest. tblastn also keeps the Stage G 162-case contract (set F).
- **Hash equality across the five platforms**: `platform_check_cases.json` has 2 tblastn and 2 blastx
  cases and none for dc-megablast, blastn-short or blastp-fast. Before the cut, a small PR adds cases
  so that every task has at least two: dc-megablast 2, blastn-short 2, blastp-fast 2, blastx +2,
  tblastn +2 (`-subject`, outfmt 6 or 7, inputs already under `LOSAT/tests/fasta`). The file stores
  argv only (no hash), so the addition changes no frozen record. Owner-delegated (standing
  instruction 2026-09-29, restated 2026-10-07).
- **NCBI executed on the other platforms**: set B's six representatives stay (blastn 2, blastp 1,
  tblastx 3); adding representatives would need a new NCBI platform characterisation of each case on
  each platform (`ncbi-only-platform-characterization.yml`) and a new authority version. Not done for
  v0.2.0; the platform claim for these tasks is therefore "same bytes as Linux x64 on every platform,
  and Linux x64 equals NCBI 2.17.0", which the release notes state in those words.

## 4. TBLASTX: all 20 Gate A cases on the candidate

`audit_tblastx_v010.py` (or set A's integrated certifier) runs all 20 cases of
`tblastx_v010_parity_manifest.tsv` on `C`, not only the 7 the v0.1.0 audit left (`v0.2.0.md`
blocker 1). Expected classifications: `p01`-`p14` EXACT_TEXT (14); `d01`-`d06` HSP_SET_DIFF under
contract `approved_db_gencode_deviation` (6): LOSAT's local `-subject` honours the non-default
`-db_gencode` where NCBI uses code 1 (PD-TBLASTX-LOCAL-SUBJECT-GENCODE, written for v0.2.0). `d06` and
the repeatability rows run three times. Any other classification is a defect to fix before GO.

Known differences shipped with v0.2.0 carry a product decision each: PD-TBLASTX-LOCAL-SUBJECT-GENCODE
(section 4), PD-NCBI-PLATFORM-VARIANCE (NCBI's own platform variance of the six representatives),
PD-LOSAT-CLI-NONSEARCH-DIFFERENCES and PD-LOSAT-NCBI-DEFECTS (outfmt 11 defline, XML2 side files, the
`-version` / `-dryrun` / `-logfile` / `-conffile` options LOSAT rejects by design),
PD-LOSAT-DATABASE-SEARCH, PD-TLOSAN-LOCAL-GENCODE-32.

On macOS the last (15th) digit of a full-precision E value (`-outfmt 11`, `-outfmt 8`) can differ by 1
from the other platforms' because of Apple's libm; the macOS tests accept exactly that
(PD-LOSAT-PLATFORM-LIBM, Owner 2026-10-25), and the claim "byte-identical to Linux x64" for the
macOS rows is read with that exception.

`LOSAT_X_*`, `LOSAT_TIMING`, `LOSAT_X_STATS`,
`LOSAT_X_REACH` and `--features diagnostics` are development variables outside the certified
configuration (README states this).

## 7. Order of the runs on the cut day

1. `C` = head of dev with green PR CI and green nightly; the always-on switch graduation PRs and the
   pre-cut document PRs merged. `promote/<date>` PR to `main` (platform-checks run there); merge;
   `release/0.2` at that commit (Owner).
2. Dispatch in parallel (the session; `gh workflow run <file> --repo satoshikawato/LOSAT --ref <ref>`):
   `platform-native-certification.yml -f candidate_sha=C` (ref `main`), `platform-checks.yml -f set=full`
   (ref `main`; the promotion push also starts one), `nightly.yml` (ref `main`), `wasm-threading.yml -f
   candidate_sha=C -f include_serial_compatibility=true` (three times, serially).
3. Locally, under `oracle.lock`, one after another: set A (`certify_integrated_runtime_v010.py`, always with
   `--wasm-bin $BT/wasm32-wasip1/release/losat.wasm`, because the default path differs; `$BT` is the cargo
   target directory of the candidate build; the output directory is an empty directory under `/tmp`), set D
   (`TMPDIR=/tmp` for `run_oracle.py`, then `check_losat.py` at 1, 2, 4 threads), set E
   (`db_search_fixtures.py freeze` in a scratch checkout, then the second `freeze --ncbi-bin
   /home/kawato/micromamba/bin --only db.sa.sam`, `git status --porcelain` empty, `check`).
4. ws, node 1: set J (memory table, speed grid, v0.1.0 pair timing).
5. Fill the contract (`candidate_sha`, run ids, evidence sha256), write the GO record and release notes,
   commit on `release/0.2` as `R`; dispatch `release-readiness-v020.yml -f candidate_sha=R`
   (the workflow must exist on `main` to be dispatchable; it reaches `main` with the promotion).
6. Owner: GO, tag `v0.2.0` on `R`, GitHub Release with the eight artifacts and `SHA256SUMS`, Bioconda.

Evidence: small logs, manifests and hashes under `docs/evidence/release_v020/`; run output over 1 MiB
or 100 files goes to a GitHub release asset per `AGENTS.md` ("Evidence and Run Output") with
`README.md` and `MANIFEST.tsv` in the directory.

## 8. Not certified in v0.2.0

psiblast (not shipped), protein scoring beyond BLOSUM62 11/1 and `-comp_based_stats 2` (blastp-short,
tblastn-fast rejected at the command line), `-parse_seqids` databases, the Web GUI's search results
(preview), and any configuration with a `LOSAT_X_*` variable set. The threaded Wasm binary is
supported, not certified (section 6).

- LOSAT Web prepares the engine for a search before "Add to queue": once the search form's options are valid and both inputs are indexed, it starts the engine worker, the instance and the thread workers that the search will use (or the renewal that it would make). In headed Chromium on the i9, the first search of a page spent 24-57 ms between "preparing" and "running" instead of 129-240 ms (TBLASTX p03, 8 and 16 threads, 4 pairs each). Reports do not change.
- LOSAT Web compiles the engine modules while they download (`WebAssembly.compileStreaming`) and still checks their SHA-256 before anything uses them; the site serves them, whose names carry their digest, with `Cache-Control: public, max-age=31536000, immutable`. Chromium then keeps compiled code with them: a later visit to the site starts from it. Chromium 149 kept the threaded module's code only after a visit that had compiled 1 MB of optimized code (here TBLASTX, BLASTP, BLASTN and TBLASTN searches); after that, the first TBLASTX p03 search of a new browser process took 433 ms against 411 ms for its second. After a visit with searches of one program it did not keep it (its 2-second caching timer did not fire), and the first search stays about twice as long as the later ones. Reports do not change.
- The Node threaded runner (`LOSAT/tests/wasi_thread_host.js`) keeps the shared-memory guard's output by default (`LOSAT_WASI_GUARD_CACHE` unset: `losat/wasi-guard` in the user's cache directory, the 8 entries used last; `0` turns it off): the guard took 150-220 ms per run of the threaded command and a cache hit takes 9-13 ms. TBLASTX p03 at 8 threads on the i9: 0.83-1.05 s instead of 0.95-1.18 s (8 pairs). Reports do not change.

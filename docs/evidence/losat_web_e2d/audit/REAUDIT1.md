# R audit of A1 fix (non-UTF-8 option values)
started; harness: scratch/h.py (runs LOSAT-head, LOSAT-final, NCBI with byte argv)

## Item 1 (t1.py) : 8736 comparisons (HEAD, FINAL, NCBI each; 3 runs per case => 26208 runs)
4 programs x {-query_loc,-subject_loc} x 21 values (leading/middle/trailing bad bytes, lone continuation, overlong, surrogate ED A0 80, >U+10FFFF F4 90.., F8.., truncated seqs, empty value) x {=, separate} x 12 companion states (none, -outfmt 99, -outfmt xyz, -evalue abc, -bogus, -bogus 1, -outfmt (missing value), -help, -version, -num_threads 0, -max_target_seqs -1, -dust zz) x {before, after} + missing -subject / loc-only / other loc valid.
Result: every case where all tokens before the first non-UTF-8 value are valid and parse OK -> FINAL gives "the value of -X is not UTF-8 ... not supported by LOSAT's <PROGRAM>" (6320+160+640 cases). 1240 cases do not carry that message: an EARLIER ordinary parse error (unknown option -bogus/-dust, "-outfmt" swallowing -query ...) reports first; HEAD identical to FINAL there (parser class, NCBI USAGE rc1 / LOSAT rc2).
Observation R-1 (low): `-help` as FIRST word then a non-UTF-8 value (e.g. blastn -help -query Q -subject S -subject_loc $'1\xffx'): HEAD printed LOSAT's help, rc 0 (NCBI: its USAGE, rc 0); FINAL rejects explicitly, rc 2 (160 cases). `-help` after the bad value: HEAD rc 2 (invalid UTF-8), FINAL explicit rc 2.

## Item 2 (t2.py): 3125 comparisons (HEAD, FINAL, NCBI)
5 programs (incl. blastx) x all options of each program's -help plus ~35 NCBI options LOSAT lacks (+bogus), 5 non-UTF-8 values x {=, separate}; bad values in -evalue/-outfmt/"6 <bad>"/-task; 18 odd option names (-\xff, -ev\xffalue=3, --\xff, -help\xff, -=\xff, bare \xff ...) in 3 positions; non-UTF-8 -query/-subject/-out (=/separate, nonexistent and existing files with non-UTF-8 names, outfmt 0/6/7); -help/-bogus/repeat/`--` combinations with a bad value.
Results (FINAL): the four programs: every non-UTF-8 option VALUE reached is rejected explicitly ("the value of -X is not UTF-8 ... not supported by LOSAT's <PROG>", rc 2); no panic, no empty message, no search ran with a wrong value (no non-empty stdout in any non-UTF-8 case except -help). Non-UTF-8 option NAMES / flags: still parser errors (rc 2) but now name the word (HEAD: "unknown option or argument ''"; FINAL e.g. "'-ev\u{fffd}alue'") -> better, not worse. A flag with =<bad> -> "-X is a flag and does not take a value" (HEAD: unknown option ''), also unchanged text class for UTF-8 flags.
-query/-subject/-out: separate form unchanged (file name rejection "file name ... is not UTF-8", rc 1, HEAD==FINAL). Inline `-query=<bad>` / `-subject=<bad>` / `-out=<bad>`: HEAD "unknown option ''", FINAL "the value of -query is not UTF-8 ... not supported by LOSAT's X" (new explicit rejection of the inline form; the diff comment says path options keep previous handling, but the `Some(_) =>` arm at cli.rs line ~150 fires before the name exemption). Not a regression.
blastx (non-search): HEAD==FINAL byte-identical in all 625 cases with non-UTF-8 values (invalid UTF-8 clap error / unknown option '' ... as before).

## 1. Display side: how the Query/Sbjct rows of a tblastx alignment are built

Call path (outfmt 0):
`tblastx_app.cpp:145-157` passes `opt.GetQueryGeneticCode()`, `opt.GetDbGeneticCode()` -> `CBlastFormat` (`blast_format.cpp:96`) -> `PrintOneResultSet` (`blast_format.cpp:1553-1585`: `s_SetFlags` adds `eTranslateNucToNucAlignment` for tblastx, lines 650-652; `display.SetMasterGeneticCode(m_QueryGenCode); display.SetSlaveGeneticCode(m_DbGenCode);` lines 1579-1580) -> `CDisplaySeqalign::DisplaySeqalign` (`showalign.cpp:1911`) -> per Seq-align `x_GetAlnVecForSeqalign` (1817-1866: Std-seg -> `CreateDensegFromStdseg` -> `CreateTranslatedDensegFromNADenseg`, Seq_align.cpp:953-999: lens/3, widths=3, throws if a length is not divisible by 3) -> `avRef->SetGenCode(m_SlaveGeneticCode); avRef->SetGenCode(m_MasterGeneticCode, 0);` (1952-1953; alnvec.hpp:396-410: row -1 sets all rows) -> `x_DisplayAlnvecInfo` (3956) -> `x_PrepareRowData` (1200; per row `m_AV->GetWholeAlnSeqString`, 1281) -> `CAlnVec::GetWholeAlnSeqString` (alnvec.cpp:199-285; segment range `[start, start+3*seg_len-1]`) -> inline `CAlnVec::GetSeqString` (alnvec.hpp:287-313) -> `CAlnVec::TranslateNAToAA` (alnvec.cpp:893-923) -> `CTrans_table` (`Genetic_code_table.cpp`: `x_InitFsaTable` 90-136, `x_InitFsaTransl` 139-241).
`GetAlnSeqString` (alnvec.cpp:145) is only called by `aln_printer.cpp`; `CSeqTranslator::Translate` in showalign.cpp (698/1116/1143) is reached only with `eShowTranslationForLocalSeq`/CDS features, never for tblastx (width 3 guards, lines 1319-1327).

Tabular (outfmt 6 and 7) uses the same machinery: `blast_format.cpp:826-827` (`tabinfo.SetQueryGeneticCode/SetDbGeneticCode`), `tabular.cpp:915-924` (translated Dense-seg), `tabular.cpp:982-986` (`alnVec->SetGenCode(m_QueryGeneticCode, 0); alnVec->SetGenCode(m_DbGeneticCode, 1);` `GetWholeAlnSeqString`), and `tabular.cpp:997-1022` recomputes `num_ident`, positives, mismatches from those strings. So `pident`/`mismatch` of every default tblastx outfmt 6/7 row come from the displayed letters, not from the engine.

Items asked for (display):
- Genetic code per row: row 0 (Query) = `-query_gencode`, row 1 (Sbjct) = `-db_gencode` (both default 1). Allowed values (blast_args.cpp:1003): 1-6, 9-16, 21-31, 33 (26 codes; ID 32 exists in gc.inc but is rejected by the CLI).
- Reverse complement: `x_GetSeqVector` (alnvec.cpp:108-142) takes the Bioseq in IUPAC coding with strand minus for a minus row; `GetSeqString` maps the plus-strand range `[from,to]` to `[size-to-1, size-from)` of that reverse-complemented vector (alnvec.hpp:296-302). IUPAC complement (A/T, C/G, R/Y, M/K, B/V, D/H, S, W, N). The Dense-seg is NOT reversed for width-3 minus rows (showalign.cpp:1852-1861), so minus rows run in alignment order with descending coordinates.
- Ambiguous IUPAC codons (`x_InitFsaTransl`, Genetic_code_table.cpp:171-207): expand each base A,C,G,T; all expansions equal -> that residue. First difference: {D,N} -> `B`, {E,Q} -> `Z`, {I,L} -> `J`, else `X`; the result is sticky (X stays X; B only stays B with further D/N, etc.). Not a vote: it is a running merge in A,C,G,T order. Codons containing a gap/illegal base: `X` (line 157 default).
- N: expands to all four bases (`NNN` -> X; `GCN` -> A; `TAN`-> X).
- Gaps/illegal letters: `sm_BaseToIdx` maps every byte other than the 15 IUPAC letters (both cases), `U`->T, `X`->N to 0 = gap. Not reachable from FASTA: CFastaReader drops `-` ("Hyphens are invalid and will be ignored") and `X`/`*` ("Ignoring invalid residues") with a warning; `U` is accepted and acts as T (oracle: `UUU`/`AUG` pair with `TTT`/`ATG` at 100%).
- First codon: no special handling. `TranslateNAToAA` never reads the start table (m_OrfStart). Oracle (code 11, HSP starting at the first codon): CTG->L, TTG->L, GTG->V, ATA->I, ATG->M, TAA->`*` (t10_*.fa). `fIs5PrimePartial` etc. are CSeqTranslator concepts and are not used here.
- Stop codons: `*` (ncbieaa of the table).
- Lowercase input: Bioseq data are IUPAC uppercase; lowercase in the FASTA never reaches the row. Lowercase in a row only marks masked intervals (SEG), applied after translation. Oracle: with `-seg no` and 50% lowercase ambiguous codons no lowercase letter appears in any row (t5_fwd_1.txt).
- Partial codon: `TranslateNAToAA` throws `CAlnException(eTranslateFailure)` "NA size expected to be divisible by 3"; unreachable for BLAST HSPs because segment lengths are multiples of 3 (Seq_align.cpp:979-989) and HSPs end inside the sequence.

## 2. Search side

- Query: `x_AutoDetectGeneticCodes` (blast_objmgr_tools.cpp:110-173) sets the per-query code to `-query_gencode` when it is not 1 (FASTA has no Source descriptor, so otherwise 1). `SetupQueries_OMF` (blast_setup_cxx.cpp:548-588) fetches the query in ncbi4na (both strands) and calls `BLAST_GetTranslation(seq+1, seqbuf_rev, na_length, frame, &buf[offset], gc)` for each context 0..5 with `query_length>0`. `gc` = `FindGeneticCode` (blast_aux.cpp:588-624: `CGen_code_table::GetNcbieaa`, `CSeqportUtil::Convert` to ncbistdaa), the same ncbieaa string the display uses.
- `BLAST_GetTranslation` (blast_util.c:427-456): codon i at index `|frame|-1 + 3i` on the plus strand (frame>0) or on `query_seq_rev+1` (reverse complement via `GetReverseNuclSequence`, 807-837; ncbi4na bit-reversal); stops when fewer than 3 bases remain; `NULLB` sentinel before and after; no start-codon logic; `*` is ncbistdaa 25. Frame order (BLAST_ContextToFrame, 839-868): +1,+2,+3,-1,-2,-3.
- `s_CodonToAA` (blast_util.c:369-425): all expansions equal -> that residue, otherwise X (21). No B/Z/J. A codon with a 0 nibble returns 0 and is dropped (`IS_residue` check) - unreachable for FASTA input.
- Subject, preliminary stage (blast_engine.c:747-785): the translated subject frames are built from the COMPRESSED 2-bit subject (`BLAST_GetAllTranslations(backup.sequence, eBlastEncodingNcbi2na, ...)`, blast_util.c:1045-1139, table `s_BlastGetTranslationTable` 989-1042), where every ambiguous/N subject base was replaced by a pseudo-random compatible base when the 2na copy was built (`s_Ncbi4naToNcbi2na`, blast_objmgr_tools.cpp:424-480, `CRandom random(base_length)`; `SetupSubjects_OMF` keeps the ncbi4na copy in `sequence_start` and puts the compressed one in `sequence`, blast_setup_cxx.cpp:836-852). So seeding and the X-drop extension see random residues at ambiguous subject codons.
- Subject, re-evaluation (blast_hits.c:2643-2720, called from blast_engine.c:1491-1497 for ungapped searches): the ncbi4na subject is fetched again (`seq_arg.encoding = eBlastEncodingNcbi4na`) and translated by `BlastTargetTranslationNew` (blast_util.c:1267-1320) -> `BLAST_GetTranslation` + `s_CodonToAA` (ambiguity -> X). `Blast_HSPReevaluateWithAmbiguitiesUngapped` produces the final raw score/extents; `Blast_HSPGetNumIdentitiesAndPositives(query_nomask, ...)` gives the engine `num_ident` (X==X counts as identity). This engine num_ident is overridden by the display strings in tabular output.
- Subject genetic code (blast_setup_cxx.cpp:796-810): `genetic_code_id = subjects.GetGeneticCodeId(i)`. For a local `-subject` FASTA the subject source is a `TSeqLocVector` handled by `MultiSeqBlastSeqSrcInit` (local_db_adapter.cpp:133-135 -> seqsrc_multiseq.cpp:131-173 -> `SetupSubjects` blast_objmgr_tools.cpp:413-421), built WITHOUT options, `SSeqLoc.genetic_code_id` defaults to `BLAST_GENETIC_CODE` (1), and there is no Source descriptor. `GenCodeSingletonFind(1)` is non-NULL (code 1 is registered by every `CBlastOptions`), so `subj->gen_code_string = <code 1 table>`. The fallback to `db_options->genetic_code` (= `-db_gencode`, blast_engine.c:1458-1468; traceback blast_traceback.c:1579-1596) is therefore never taken. Result: the local-subject search always translates the subject with code 1; `SetDbGeneticCode` (blast_options_cxx.cpp:2411-2420) only registers the table and stores the value.

## What the port must do (each item with NCBI file:line)
1. Build the Query/Sbjct rows by translating the HSP's nucleotide range per codon with the DISPLAY rule (B/Z/J merge of {D,N},{E,Q},{I,L}, else X), query with `-query_gencode`, subject with `-db_gencode` regardless of what the search used (showalign.cpp:1952-1953; Genetic_code_table.cpp:171-207; alnvec.cpp:893-923). No start-codon logic, stop `*`, uppercase letters, minus rows = IUPAC reverse complement in alignment order (alnvec.hpp:296-302).
2. Compute Identities, Positives and the midline from the displayed letters with the display matrix (only `ARNDCQEGHILKMFPSTWYVBZX` and `*`; J = -1000) (showalign.cpp:2120-2157; align_format_util.cpp:3549-3582), and use the same displayed-letter counts for outfmt 6/7 `pident`/`mismatch` (tabular.cpp:982-1022) instead of the engine `num_ident`.
3. Keep the search translation separate: query with `s_CodonToAA` semantics (done), subject re-evaluation with 4na `s_CodonToAA` (done), preliminary subject frames from the length-seeded random 2na resolution (blast_objmgr_tools.cpp:424-480; blast_engine.c:772-775) - currently missing for TBLASTX.
4. Local `-subject`: NCBI searches the subject with code 1; LOSAT's approved exception searches with `-db_gencode`; keep the report (rows, counts, `pident`) identical to NCBI's by always using `-db_gencode` for the Sbjct row (blast_setup_cxx.cpp:796-810; blast_format.cpp:1580).
5. `-query_gencode`/`-db_gencode` accept exactly 26 ids (blast_args.cpp:1003); all are present in gc.inc, so `GetTransTable` never throws (Genetic_code_table.cpp:555-557).

## Open points / cross-range observations
- The cause of the N-island HSP differences is attributed to the 2na random resolution from the source (blast_engine.c:772, blast_objmgr_tools.cpp:424-480) and the observed dependence on subject length; I did not emulate `CRandom` to reproduce NCBI's exact HSP list. Verify by wiring `resolve_ncbi4na_to_ncbi2na` into the TBLASTX subject frames and diffing against `t8_*`/`t9_s.fa`.
- `algorithm/tblastn/stage_e_report.rs:632-700` renders subject residues from the search translation buffer (`NCBISTDAA_TO_AA`), so a TBLASTN report would show `X` where NCBI's display (same `TranslateNAToAA`) shows `B`/`Z`/`J` for the same codon classes. Not examined further (outside range F).
- `blast_format.cpp:1519-1521` (`PrepareBlastUngappedSeqalign` for ungapped searches) is not part of this range; I assumed one Seq-align per HSP as the oracle output (one `Score =` block per HSP) shows.

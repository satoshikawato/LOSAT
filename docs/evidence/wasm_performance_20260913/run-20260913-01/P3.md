## Candidate selection and semantic proof

The selected experiment changes only the contiguous inner-span write in `align_ex_protein_impl`. `gap_alloc_trace_row` clears a reused row, and `band_start` equals the captured `orig_b_index`. Enumeration visits consecutive indices; every non-fence cell writes once, including X-drop-discarded cells. Hence before each write `row.len() == band_index == b_index - orig_b_index`, and the general helper always takes its existing push branch. The candidate uses push directly and asserts the invariant in debug builds. It leaves the tail-expansion helper, final row size, scores, ties, matrix dispatch, fences and edit-script reconstruction intact.

This removes repeated dispatch in the dominant mapped DP function; the actual whole-process improvement is still unproven. The independent read-only auditor verified the invariant against current Rust and NCBI sources. Existing reuse tests compare every used row byte and offset across standard/adjusted matrices, forward/reverse scans, changing bands and empty inputs. The isolated test extension adds a fence before the first row write in both orientations.

An alternative cache hypothesis was inspected but not implemented: query-parallel Kappa currently creates a subject SEG cache per query, giving zero hits and80,611/111,293 misses in the two main n8 diagnostics. The existing serial cache produces80,016 hits/595 misses on the first input. Source audit supports within-search cache reuse after the per-query near-identical/SEG gate, but Wasm sampling does not establish enough SEG cost to select it ahead of DP. `map_init` would create job/folder-local caches, not necessarily eight worker caches. Existing byte counters omit cache insertion clones and sentinels, so they are logical accounted range bytes, not physical-copy/allocation counts. No new cache lifetime or matrix/CBS/SEG behavior is introduced.

## Final decision

All18 exploration processes passed (two fresh oracles, four diagnostic gates, twelve measured cold runs), with exact raw parity. At threaded n8, AP027078/AP027131 median changed from6.906908 to7.210050 s (4.39% slower), and AP027132/NZ median changed from10.453639 to10.196128 s (2.46% faster). Full samples and ranges are in `p3-exploration/summary.json`. Maximum RSS was308,043,776→308,109,312 bytes and328,818,688→322,297,856 bytes respectively.

The candidate is rejected after the declared three-repeat exploration because neither main input reaches10% improvement. It is not integrated. No warmup-plus-five adoption run, native/serial candidate performance expansion, candidate matrix/retry/format sweep, or candidate reuse/memory certification is claimed. Additional cache/layout ideas remain hypotheses; unsupported attribution is not converted into an optimization claim. The tested prototype does not establish the per-instruction cause of remaining DP cost.

P4 therefore starts from the unchanged original production source and normal Node settings, with the adopted comparison/measurement changes only.

The isolated expanded unit test `test_traceback_contiguous_rows_reused_scratch_matches_fresh` passed in a release build (1 passed,420 filtered; `p3-candidate-unit.log`). This validates the candidate test only and does not turn its rejected performance result into adoption.

# LOSAT v0.1.0 Release Readiness Plan

この文書は、LOSAT v0.1.0 を正式リリースする前に残っている
ブロッカーと作業をすべて潰すための実行計画である。

方針は以下を優先する。

- 機能追加ではなく、リリース範囲の固定、NCBI parity 証跡、配布物整備を優先する。
- NCBI BLAST C/C++ 実装を唯一の挙動基準にする。
- LOSAT runtime/build/feature path から NCBI BLAST+ executable/library へ委譲しない。
- サポート対象外の挙動は、暗黙の fallback ではなく明示的な unsupported/unimplemented error にする。
- 実装変更を行う場合は、AGENTS.md に従い、該当する NCBI C/C++ 参照コメントを追加する。

## Release Candidate Gate

v0.1.0 release candidate は、以下をすべて満たした場合のみ作成する。

- `git status --short --branch` が意図した変更だけを示す。
- release scope が README、CLI help、CHANGELOG、GitHub Release 本文で一致している。
- サポート対象内に既知の NCBI divergence がない。
- 承認済み例外である TBLASTX local `-s/--subject` non-default `--db-gencode`
  の挙動が、README と release notes に明記されている。
- `cargo fmt --check`、`cargo clippy`、`cargo test`、`cargo build --release` が通る。
- サポート対象プログラムの NCBI comparison fixture が current commit で再実行され、
  NCBI BLAST+ version、LOSAT commit、コマンド、入力、差分結果が保存されている。
- Native/Wasm の配布対象が明確で、各成果物に checksum と build metadata がある。
- 生成物、debug 出力、退避ファイル、不要な test output が release tree に混入していない。
- CI または手動 release checklist のどちらかで、上記 gate を再現できる。

## Phase 1: Repository Hygiene

目的: release tree に不要生成物や曖昧な fixture を混ぜない。

作業:

1. 作業ツリーを確認する。

```bash
git status --short --branch
git ls-files --others --exclude-standard
git ls-files LOSAT/tests/losat_out LOSAT/tests/blast_out LOSAT/tests/ncbi_out
```

2. test output を三分類する。

| Type | Policy |
| --- | --- |
| Canonical fixture | 小さく、目的が明確で、release に残す |
| Generated comparison output | commit せず、release artifact または scratch に保存 |
| Debug scratch | 削除する |

3. `LOSAT/.gitignore` を見直す。

- CLI app として配布するなら `Cargo.lock` は原則 track する。
- `tests/losat_out/`、`tests/blast_out/`、`tests/ncbi_out/`、`__pycache__/`、
  `*.pyc`、`*.tmp`、`*.orig`、temporary logs を ignore 対象にする。
- 残す fixture は ignore から除外し、用途を README または tests docs に書く。

4. 退避ファイルと一時ファイルを処理する。

- `LOSAT/src/algorithm/tblastx/utils.rs.orig` が不要なら削除する。
- `LOSAT/.tmp` が不要なら削除する。
- `__pycache__` と `.pyc` は削除する。

5. 大きいファイルを棚卸しする。

```bash
find . -type f -size +10M -print
du -sh LOSAT/tests/losat_out LOSAT/tests/blast_out LOSAT/target 2>/dev/null
```

完了条件:

- release branch の `git status` が意図した tracked changes のみを示す。
- generated output を再生成する手順がある。
- release source archive に不要な debug scratch が入らない。

## Phase 3: Runtime Hardening

目的: 正常系で panic/debug output が出ず、未対応機能が明示的に失敗する状態にする。

作業:

1. panic/unwrap/expect を棚卸しする。

```bash
rg -n "panic!|todo!|unimplemented!|unwrap\\(|expect\\(|dbg!|eprintln!|println!\\(" LOSAT/src
```

2. 通常実行で stderr が汚れないことを確認する。

- `LOSAT_STARTUP_TRACE` など debug env がない状態で実行する。
- progress/timing/debug 出力が通常時に出る箇所を修正する。
- debug env 配下の出力は残してよい。

3. unsupported path を明示化する。

- 未対応 option は silently ignored にしない。
- NCBI に fallback しない。
- error message は option 名、program、理由を含める。

4. NCBI runtime dependency がないことを確認する。

```bash
rg -n "Command::new|blastp|blastn|tblastx|makeblastdb|ncbi" LOSAT/src LOSAT/build.rs Cargo.toml
```

5. CLI smoke tests を追加または確認する。

- `losat --help`
- `losat blastn --help`
- `losat tblastx --help`
- `losat blastp --help`
- unsupported option error。
- missing input file error。
- malformed FASTA error。

完了条件:

- normal CLI run の stderr が NCBI BLAST+ と比較可能な状態に保たれる。
- release supported scope の入力で panic が確認されない。
- unsupported behavior は explicit error で止まる。

## Phase 4: Native NCBI Parity Sweep

目的: サポート対象挙動が NCBI BLAST+ と一致することを current fixture で証明する。

共通ルール:

- NCBI BLAST+ executable は comparison oracle としてのみ使う。
- oracle version を必ず保存する。
- hit count だけで合格にしない。
- coordinates、raw score、bit score、E-value、ordering、formatting を比較する。
- 既知差分が出た場合は、対応する NCBI source path を特定してから修正する。
- 差分が残る場合、その scope は v0.1.0 supported に入れない。

共通 setup:

```bash
cd LOSAT
cargo build --release
target/release/LOSAT --version
tblastx -version
blastn -version
blastp -version
```

### BLASTN

作業:

1. 現行 fixture を再実行する。

```bash
cd LOSAT/tests
bash run_comparison.sh
python3 compare_blastn_parity.py
```

2. `blastn_parity_manifest.tsv` の全 case について、以下を保存する。

- query file。
- subject file。
- task。
- command line。
- LOSAT output path。
- NCBI output path。
- diff summary。
- pass/fail。

3. megablast と `--task blastn` を分けて合否判定する。

4. 既知 active parity work が残る場合:

- 再現 fixture を一つに絞る。
- NCBI source path を特定する。
- 修正する。
- 修正できない場合は BLASTN を experimental または limited support に落とす。

完了条件:

- supported BLASTN scope の fixture が bit-perfect。
- active BLASTN divergence が release note に残らない。

### TBLASTX

2. resolved regression target を固定する。

- NCBI local `-subject` non-default `db_gencode` output をこの一点の failure oracle にしない。
- その他の scoring/order/filter/statistics/formatting は NCBI parity required。

4. TBLASTX `n1` と multi-thread run の出力順序を確認する。

```bash

```

完了条件:

- supported TBLASTX fixture が approved exception を除いて bit-perfect。
- exception が README、CHANGELOG、release note に明記されている。
- multi-thread output が NCBI order に reduce される。

## Phase 8: Final Release Procedure

目的: release を切り、post-release の状態まで整える。

作業:

1. release commit を作る。

```bash

git add README.md CHANGELOG.md docs/release/v0.1.0.md LOSAT/Cargo.toml LOSAT/Cargo.lock

```

2. final gate を実行する。

```bash
cd LOSAT
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo build --release
cargo package --list
cargo publish --dry-run --locked \
  --config 'build.target-dir="/tmp/losat-cargo-publish-target"'
```

4. tag を打つ。

```bash

git push origin release/v0.1.0
git push origin v0.1.0
```

5. GitHub Release を draft で作成する。

- release notes。
- supported scope。
- known limitations。
- approved TBLASTX db_gencode exception。
- artifacts。
- checksums。
- verification summary。

6. crates.io に出す場合:

```bash

```

- `main` に release branch を merge する。
- 次版を `0.1.1-dev` または `0.2.0-dev` 相当に進める方針を決める。
- milestone/issue を整理する。

完了条件:

- Git tag、GitHub Release、artifact checksum、release notes が一致する。
- post-release branch が次の開発状態に戻っている。

## Risk Register

| Risk | Impact | Mitigation |
| --- | --- | --- |
| BLASTN active parity work remains | Cannot claim full BLASTN support | Fix current fixture or mark limited/experimental |
| BLASTP parity/performance remains secondary | README and CLI may overpromise | Mark BLASTP experimental unless full fixture passes |
| TBLASTX local db_gencode differs from NCBI local subject behavior | Users may report expected exception as bug | Document narrow approved exception prominently |
| Generated outputs are accidentally shipped | Bloated release and unclear provenance | Clean tree, ignore generated dirs, package list review |
| Cargo.lock policy is inconsistent | Reproducibility ambiguity | Track lockfile for CLI release or document library-only policy |
| Existing clippy debt blocks `-D warnings` | CI/release gate cannot pass | Either fix or narrowly allow documented lints without changing BLAST behavior |
| Full unit suite has 8 known failures | Release cannot claim a clean quality gate | Fix each failure against NCBI source or explicitly descope affected behavior |
| CI lacks NCBI oracle | Parity regressions can slip | Manual full parity gate plus optional manual workflow |
| Wasm threading runtime support varies | User-visible failure or nondeterminism | Keep threaded Wasm experimental unless runner matrix passes |

## Suggested Execution Order

1. Phase 0: freeze scope.
2. Phase 1: clean repository and ignore policy.
3. Phase 2: update metadata/docs for the frozen scope.
4. Phase 3: harden CLI/runtime edges.
5. Phase 4: run native NCBI parity sweep and fix any supported-scope divergence.
6. Phase 5: run Wasm parity only for targets that will be released.
7. Phase 6: add CI/release automation.
8. Phase 7: package and dry-run.
9. Phase 8: tag and publish.

Do not proceed to tag creation while any P0 item is unresolved.

## D. Defects found outside the report writer, and their handling

The fixtures were first checked in outfmt 6: a fixture can only match in outfmt 0 if LOSAT finds the same HSPs. [`precheck_hits.py`](precheck_hits.py) runs each manifest search with `-outfmt 6` in both programs. On engine `edf825d36`, 33 of 34 fixtures match NCBI; the exception is D.2 ([`run-20260929T000046Z/precheck-edf825d36.tsv`](run-20260929T000046Z/precheck-edf825d36.tsv)).

### D.1 Coordinate width in the BLASTP and TBLASTN reports (existing defect)

NCBI sizes the coordinate column from the largest **0-based** start or stop over both rows (`showalign.cpp:1366-1367`, quoted in A.8), and `AddSpace` takes a `size_t`, so a 1-based start with one more digit gets a single space. LOSAT's `write_alignment_with_sequences` (`pairwise.rs:452-453`, BLASTP) and `write_tblastn_alignment` (`pairwise.rs:2008-2014`, TBLASTN) take the digits of the largest **1-based** coordinate. They differ from NCBI exactly when the largest 1-based coordinate is a power of ten:

| Fixture | NCBI 2.17.0 | LOSAT `edf825d36` |
|---|---|---|
| `width.blastp` | `Sbjct  100 N  100` (width 2) | `Sbjct  100  N  100` (width 3) |
| `width.tblastn` | `Sbjct  2   RVRR…  100` | `Sbjct  2    RVRR…  100` |

BLASTX's `write_blastx_alignment` already follows NCBI (`pairwise.rs:2616-2625`). Handling (the recommended option, recorded without a maintainer decision under the session rules): S07 computes the width in one helper that follows `showalign.cpp:1366-1367` and uses it from the BLASTP, TBLASTN and new BLASTN code; S08 uses it for TBLASTX. BLASTX's function is not changed (DW-10). The change alters BLASTP and TBLASTN outfmt 0 bytes only at that boundary, so S07 must list every frozen output (Gate A, the Stage G matrix, the BLASTP manifest) whose hash changes, and show that each change matches the NCBI output of that case. `width.blastp` and `width.tblastn` are the fixtures for it. The TBLASTN outfmt 0 certified for TLOSAN v0.2.0 is the same code, so it has the same defect at this boundary; its certified fixtures do not reach it.

### D.2 BLASTN panic in the gapped-start search (existing defect)

`-task blastn -word_size 7` or `8` on `multi_query.fasta` × `multi_subject.fasta` panics at `LOSAT/src/algorithm/blastn/alignment/gapped.rs:559` (`index out of bounds: the len is 400 but the index is 18446744073709551615`), with any E-value. `blast_get_start_for_gapped_alignment_nucl` walks backwards from the gapped start and stops at the query start but not at the subject start. NCBI's loops check the query pointer only:

```c
/* src/algo/blast/core/blast_gapalign.c:3340-3349 */
    while ((q-query < q_len) && (*q++ == *s++)) {
        score++;
        if (score > hspMaxIdentRun) return;
    }
    q = query + q_start;
    s = subject + s_start;
    while ((q-query >= 0) && (*q-- == *s--)) {
        score++;
        if (score > hspMaxIdentRun) return;
    }
```

They stop at the subject ends because the subject buffer has sentinel bytes. The traceback passes `subject = subject_blk->sequence;` (`src/algo/blast/core/blast_traceback.c:342`) to `BlastGetStartForGappedAlignmentNucl(query, subject, hsp);` (`blast_traceback.c:457`). For a local subject that pointer is one byte past a sentinel: `src/algo/blast/api/seqsrc_multiseq.cpp:353-358` (`That buffer has an extra sentinel byte for blastn` … `args->seq->sequence = args->seq->sequence_start + 1;`). The buffer has sentinels at both ends (`src/algo/blast/api/blast_setup_cxx.cpp:1219-1225`: `case eBlastEncodingNucleotide: // Used for nucleotide blastn queries` / `if (sentinel == eSentinels) {` … `retval = sequence_length + 2;`), and the sentinel is `const Uint1 kNuclSentinel = 0xF;` (`src/algo/blast/core/blast_encoding.c:121`), which differs from every base code, so the comparison fails there and the loop ends. The Rust equivalent stops the backward walk when the subject index is 0, and the forward walk at the subject length. A scratch build with exactly that change ([`run-20260929T000046Z/probe-gapped-start-bound.diff`](run-20260929T000046Z/probe-gapped-start-bound.diff)) matched NCBI outfmt 6 byte for byte on this input at word sizes 4–8 with E-values 10 and 1000 (up to 3,762 HSPs), and on all 34 fixtures ([`run-20260929T000046Z/precheck-probe.tsv`](run-20260929T000046Z/precheck-probe.tsv)). The worktree file was restored afterwards; no code is committed in S06. Handling: S07 fixes it first, as its own engine change with this NCBI reference and a regression test on `multi.ws7_e1000.blastn`.

### D.3 BLASTN writes no NCBI warnings to stderr (existing gap)

NCBI writes `Warning: [blastn] Examining 5 or more matches is recommended` when `-max_target_seqs` is below 5 (`blast_args.cpp:2975-2977`, A.1), and for an invalid query `Warning: [blastn] Query_1 allN query of only N: Could not calculate ungapped Karlin-Altschul parameters due to an invalid query sequence or its translation. BLASTX has both (`LOSAT/src/algorithm/blastx/native.rs:386-394`, `blastx/report.rs:1698-1779`), but its builders write `[blastx]` literally, so BLASTN cannot call them without changing their bodies (DW-10). Handling: S07 adds them for BLASTN (all formats, as in NCBI) and gates stderr on the three fixtures that record it (`multi.mts3.blastn`, `multi.mts1.blastn`, `edge.allN.blastn`).

### D.5 BLASTN scoring options outside the certified profiles (existing gap)

## G. Additions from Session S07

The port found five NCBI behaviors that sections A–F did not record. Each is implemented with its NCBI reference (engine commits `032a4b96c` and `0388d1064`), and the first three have new fixtures. A sixth, G.6, is an existing LOSAT defect that the independent audit found.

**G.1 An invalid query and NCBI's query batches.** The all-N fixture of S06 (`edge.allN.blastn`) is a batch of one invalid query, which takes the `-1` path of A.5: `CheckInternalData` fails for the whole batch (`local_blast.cpp:177-207`). In a batch that also has valid queries, the invalid query's contexts are only marked invalid (`blast_stat.c:2783-2791`). Its footer then prints neither Karlin block and `Effective search space used: 0`, following `x_PrintOneQueryFooter` (`blast_format.cpp:451-478`: `if (kbp_ungap) {…}` and `if (kbp_gap) {…}`). The warning names the query by its position in the input (`Query_2`).

Which batch a query is in follows `CBatchSizeMixer`, not `GetQueryBatchSize`: for blastn that function returns 0 (`blastn_args.cpp:131-135`; `blast_input_aux.cpp:99`).
- The first batch has `max(1000000, total subject length / 3000) / 200` residues, within [100, chunk size − 1000] (`blastn_app.cpp:261-274`; `blast_app_util.hpp:69-81`; `blast_app_util.cpp:65-81`). The chunk size is 1,000,000 for blastn and 5,000,000 for megablast (`local_blast.cpp:65-73`).
- Each later batch size comes from the previous batch's ungapped extension count (`blastn_app.cpp:299-300`; `CLocalBlast::GetNumExtensions`, `local_blast.cpp:301-309`). LOSAT does not count those extensions.

The report therefore handles three cases:
- the first batch exactly;
- the later queries exactly when they are all invalid (every later batch is then invalid) or all valid;
- otherwise, outfmt 0 fails explicitly before writing, because an invalid query then follows the first batch among valid queries.

The total length reaches the mixer through `int` (`blast_format.cpp:131,136`), so the first batch is 5000 residues only for subjects below 2^31 letters. The independent audit of S07 found three limits, which S07+ handles:
- **Outfmt 7 is affected too (N1, an existing LOSAT difference).** For a query of an unsearched batch, NCBI's outfmt 7 omits `# 0 hits found`, because there is no Seq-align (`tabular.cpp:1277-1282`: `if (align_set) {`). LOSAT prints the line.
- **The fail-fast is wider than needed (N2).** NCBI clamps every batch to at least 100 residues (`blast_app_util.hpp:74`), so a run of later invalid queries shorter than 100 residues, followed by a valid query, is always searched.
- **Subjects of 2^31 letters or more (N3).** The `int` conversion is not reproduced for them.

The first version of this rule (S07, before its independent audit) used `blast_input_aux.cpp:105-113` (100,000 and 5,000,000 residues); the audit found that blastn does not use those sizes. Fixtures: `edge.mixed_allN.blastn` (one batch with valid queries) and `edge.batch_allN.{blastn,megablast}` (an all-N query that fills the first batch).

**G.2 The ungapped Karlin block depends on the query composition.** `Blast_ScoreBlkKbpUngappedCalc` (`blast_stat.c:2778-2792`) counts the context's residues in BLASTNA without `N` and the gap (`BlastResCompStr`, `blast_stat.c:2004-2013`; `blast_setup.c:349-350`). It pairs them with the standard composition through the BLASTNA matrix, whose ambiguity scores are averages over the degeneracy. An ACGT-only query gives P(match) = 0.25, which is what LOSAT's engine assumes (`ncbi_cutoffs.rs:56-74`). A query with IUPAC codes gives another block (`edge.ambig.blastn`: Lambda 0.654 against 0.634). The report computes the block per query (`algorithm/blastn/pairwise.rs::query_ungapped_karlin`). The same function decides whether a query is invalid: no counted residue, or a failed calculation. The engine's search still uses the composition-independent block for its gap trigger and ungapped X-drop; S07+ checks whether that matters (the three `edge.*` fixtures match NCBI in outfmt 6). Fixtures: `edge.ambig.blastn`, `edge.ambig.megablast`.

**G.3 The description table follows `x_InitDeflineTable`, not `x_InitDefline`.**
- `DisplayBlastDefline` calls `x_InitDeflineTable` (`showdefline.cpp:1004-1011`).
- There, a row shows the highest bit score of the subject's HSPs and that HSP's E-value (`GetSeqAlignSetCalcParams`, `align_format_util.cpp:4285-4310`).
- For the last row, the total bit score's width is assigned to the *score* width when it exceeds every earlier total width (`showdefline.cpp:1137-1142`: `if(m_MaxTotalScoreLen < sci->total_bit_string.size()){ m_MaxScoreLen = sci->total_bit_string.size(); }`).
- The last row exists only when the subjects fit in the table. A total is wider than `Total` only above 99999 bits (`%5.3le`, 9 characters).
- `AP027152_AP027202.blastn` shows it: one subject, 241 HSPs, 108,114 total bits, a score column 9 wide.
- `write_blastn_description_table` implements it.
- The table writer of BLASTP, TBLASTN and BLASTX (`write_subject_summary_table_with_sum_n`) still takes the first HSP of each subject and the plain score width. For TBLASTN with sum statistics, the first HSP need not be the highest-scoring one. No certified fixture shows a difference; S08 handles it with the TBLASTX table (§G.5).

**G.4 ABI v1 keeps BLASTN at outfmt 6 and 7.** Plan TD-1 freezes ABI v1. Its BLASTN entry (`run_web_pair`) rejects outfmt 0 with the error that it gave before (`unsupported BLASTN output format: 0`). The CLI and ABI v2 write outfmt 0.

**G.6 A lowercase query on the minus strand (existing defect, fixed).** NCBI takes both strands, in NCBI4NA, from sequence data that has no letter case (`blast_setup_cxx.cpp:977,989`: `sv.SetCoding(CSeq_data::e_Ncbi4na);` … `sv.GetStrandData(strand, buffer);`); lowercase letters are recorded as masks. LOSAT's `reverse_complement` looked up `IUPACNA_TO_NCBI4NA`, which maps only uppercase letters, so a soft-masked query without `-lcase_masking` lost its lowercase run on the minus strand, in every format. It now uppercases first. Fixtures: `mask.lcase_minus.{blastn,megablast}`.

## Worker profiles and the first long call

Successful diagnostic profiles are in `p1-profiles-ext4/`; raw V8 logs were written to ext4 because the first attempt writing profiler logs directly onto the repository filesystem exceeded worker-start timeout. Both failed attempts remain in `p1-profiles/`; their times are excluded. Successful profiled executions have exact oracle bytes. Profiler-enabled wall times are excluded from release-speed comparisons.

An independent read-only auditor checked Wasm names and compilation records. Function 1321 is `link_hsp_group_ncbi`; function 1283 is the scan closure. The normal setting has 12,224 identified linking program-counter samples in Liftoff code and nine in TurboFan code. The forced setting has 2,189 linking samples in TurboFan code. In normal mode, 12,169 Liftoff samples occur after that isolate logged the optimized allocation. This supports a long first linking call continuing in baseline-compiled code, consistent with V8's documented absence of on-stack replacement for Wasm. Four worker isolates execute linking; sampled scan work is concentrated in one of those four.

The parser maps only sampled program counters, ignores stacks and code movement/deletion, and leaves 81.8%/91.1% of ticks unmapped. Its `losat` name filter also includes JavaScript paths. Consequently these counts are not complete CPU percentages or measured worker utilization. The findings identify the compilation tier of observed Rust PCs; they do not allocate the entire speed difference among compilation, scheduling, allocation and linking.

The existing `sum_stats_linking` timer starts around the second linking pass (`run_impl.rs:2452`), after the first call at line 2305. Its small value does not measure all linking work. Both calls follow distinct NCBI engine stages.

## Timing review and remaining checks

A PemoMJNVB/LvMJNV baseline diagnostic reached the configured 300-second watchdog and remains TIMEOUT. Its reported monotonic duration is 282.0199 seconds, while coarse UTC timestamps span 300 seconds. Late evidence hashing can extend the recorded UTC interval, but cannot explain a watchdog expiring before the recorded monotonic timeout interval. The historical cause is an inference; the realtime-sensitive watchdog mechanism is now established in `clock-audit.md`. Failed time is never converted to 300 seconds of successful work. Additional realtime, boottime and GNU-time elapsed observations now accompany future runs. The clock audit subsequently established the realtime-sensitive Python wait path; monotonic deadline checks now prevent premature kills from forward realtime steps. Realtime offsets are diagnostic, while monotonic/boottime disagreement invalidates timing. This does not recalibrate monotonic to an external clock or change any old result.

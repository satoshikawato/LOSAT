## Network safety (important)
NCBI's reader tries the first line of the input as a Seq-id when it starts with a letter or digit (`CBlastInputReader::ReadOneSeq`, `blast_fasta_input.cpp:130-179`), and if it parses as an accession it fetches the sequence from GenBank over the network (the data loader). Never run an NCBI executable on an input whose very first line (before any `>` line, or in a file without `>`) starts with a letter or digit, unless the run's working directory contains a file `.ncbirc` with the two lines `[BLAST]` and `DATA_LOADERS=none` (this turns the data loaders off: `blast_scope_src.cpp:76-94`). Only the BI range may make at most 6 runs without that file, to observe the data loader path, and must list them in its notes. All other runs: work in a directory without `.ncbirc` (or with the `DATA_LOADERS=none` file when the first line starts with a letter or digit).

## Scope
- Programs and the reader flags: nucleotide input (`fAssumeNuc`): BLASTN query and subject (tasks megablast default, blastn, blastn-short, dc-megablast: reading does not depend on the task, but say so if it does), TBLASTX query and subject, TBLASTN subject; protein input (`fAssumeProt`): BLASTP query and subject, TBLASTN query. bl2seq only (`-query`, `-subject`), never `-db`, never `-remote`, no `-parse_deflines` (LOSAT rejects it; say what it would change), `-lcase_masking` on and off, `-query_loc`/`-subject_loc` only where they meet the reader (`x_FastaToSeqLoc`), outfmt 0, 6, 7 (default fields and the custom fields that show IDs and titles: `qseqid`, `sseqid`, `qacc`, `sacc`, `qaccver`, `saccver`, `stitle`, `salltitles`, `sseqid`, `qgi`, ... whichever LOSAT supports), `-num_threads`, standard input (`-query -`, `-subject -`), empty files and pipes.
- Inputs: deflines (empty, white space only, white space after `>`, control characters including tab, non-ASCII UTF-8 and non-UTF-8 bytes, `>?` gap lines `>?100`, `>?unk100`, `>?`, `>?abc`, `>?_x`, `[key=value]` modifiers, titles over 1000 characters, titles ending with 20 nucleotides or 50 amino acids, with and without trailing white space); sequence lines (IUPAC and other letters, digits, `-`, `*`, `;` comments, `!`/`#`/`;` comment lines, white space inside and around lines, U+00A0 and other non-ASCII bytes, lowercase, `U`); records without residues (some or all queries/subjects); text before the first defline (blank lines, comments, BOM, sequence without defline, an accession-like line); line endings LF, CRLF, CR only, mixed, no final newline; very long lines; the CheckDataLine error and the >40% ambiguous warning; errors and warnings in a later query batch.

## What to produce
For your range, enumerate every NCBI function (and every branch of it that the inputs select) on the reading path that can change the records (count, order, local ID, title bytes, residues, lowercase mask), warnings, errors, exit status or report bytes; follow the calls from the entry points named in your range part (include static helpers, macros with logic, and the C++ stream behaviour where it changes bytes); find the LOSAT place that corresponds; and classify each row.

`status_before` (what LOSAT does today):
- `faithful`: LOSAT already does exactly this for every input (say why).
- `divergent`: LOSAT has code for the step but gives a different result for some input (say which input and what differs).
- `unported`: no LOSAT counterpart.
- `rejected-now`: LOSAT rejects the inputs that reach this branch with a `not supported by LOSAT's` error today (cite the check).
- `exception`: an approved exception covers the difference (cite it).
- `n/a`: executes but cannot affect records, warnings, errors, exit status or output (give the reason), or is unreachable with the flags above (say which flag).

`blastx_port`: `faithful`, `divergent`, `absent` or `n/a` for BLASTX's `algorithm/blastx/input.rs`; `blastx_location` its `path:line(function)` or `-`.

`impact`: `high` (common research FASTA), `medium` (plausible inputs: CRLF, lowercase, empty records, comment lines, long titles), `low` (rare bytes or extreme sizes), `none` for faithful/n/a/exception.

`proposal`: `keep`, `port:S|M|L` (S under ~100 Rust lines, M a few hundred, L more), or `reject:<reason>` (only with a reason: network/BLAST DB data loader, out-of-scope option, an NCBI crash).

## TSV format (tab-separated, one header line, then one line per row)
`range	row	ncbi_file	ncbi_lines	ncbi_function	branch	losat_location	status_before	blastx_location	blastx_port	impact	proposal	evidence	notes`
- `row`: 1, 2, ... within your range.
- `ncbi_file` relative to `c++/`; `ncbi_lines` `start-end`.
- `branch`: prefix with the input kind and role: `nuc:` (fAssumeNuc), `prot:` (fAssumeProt), `all:`; add `q`/`s` when the role matters (e.g. `nuc-s: subject read during argument processing`). Add the program letter (`N` blastn, `X` tblastx, `T` tblastn, `P` blastp) when only some programs take the branch or when LOSAT's place differs per program (then one row per program).
- `losat_location`: `path:line(function)` relative to `LOSAT/src` (or `web/adapter/src`), `;`-separated, `-` if none.
- `evidence`: scratch file names of oracle (and LOSAT-before) runs that show the behaviour, or `source` if read only.
- `notes`: one line, concrete: what NCBI does (values, positions, message text with its exact bytes, exit code, when it is printed relative to other output), what LOSAT does today, and what must change. No tabs or newlines inside a field.

Also write `<RANGE>_notes.md`: the call path you followed (entry points, order, timing), the state that persists between records and batches (line number, pushback, EOL style, ID counter, masks), the oracle observations (command, input bytes in hex or Python literal, what NCBI prints on stdout and stderr, exit code; what LOSAT-before prints), surprises, and anything the session must decide. Oracle observations matter as much as the source reading: confirm every non-obvious claim with a small NCBI run, and keep the inputs and outputs in your scratch directory.

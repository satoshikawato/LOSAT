# Changelog

All notable release-facing changes and milestones are documented here.

## [Unreleased]

- `blastn` (all tasks) holds less memory while it searches, with the same output: the query once (one BLASTNA buffer with sentinels, as NCBI BLAST+ holds it, instead of about seven copies, with the four-base bytes of the ungapped extension computed where they are read), the final HSP lists at their exact size, and no growth slack in FASTA records of 1 MiB or more (all programs). Max RSS, same-run measurements: megablast of Sakai (5.5 Mb) against MG1655 at 8 threads 197 to 146 MiB (NCBI BLAST+ 2.17.0 `-db` 153 MiB); 100 16S queries against 28,036 16S sequences at one thread 135.5 to 109.1 MiB.
- Added `blastn -db NAME` for megablast, blastn and dc-megablast: BLASTN searches an NCBI BLAST nucleotide database (the files of makeblastdb without `-parse_seqids`, or of `LOSAT makedb`; format versions 4 and 5, several volumes, alias files as for BLASTP) and gives the output of NCBI BLAST+ 2.17.0 `blastn -db NAME -num_threads 1` for outfmt 0, 6 and 7, the same at every `-num_threads`. The search reads the stored 2-bit bases (where makeblastdb put random bases for ambiguous letters, as NCBI does) and rebuilds the ambiguity codes for the alignments, so `-db` and `-subject` of the same sequences differ where NCBI's do. The database is read in blocks of about 1 MiB; only the sequences of the hit lists are read again, one at a time. Totals above 2^31 letters are kept in 64 bits as NCBI keeps them (`-subject` keeps its limit). Added `blastn -dbsize N` for `-db` and `-subject`; `-searchsp`, `-db_soft_mask` and `-db_hard_mask` stay unsupported.
- `blastn` (all tasks) at one thread hands each subject's HSPs to the hit lists as soon as the subject is searched, as NCBI BLAST+ updates its hit lists one subject at a time, instead of holding the HSPs of every subject of a query batch until all are searched. Reports do not change. Megablast of 100 16S queries against 28,036 16S sequences (40.6 Mb) at one thread: peak memory 237 to 175 MiB (same-run measurement). With two or more threads the same is opt-in (`LOSAT_X_BNSTREAM`: the subjects are searched in blocks of 64 per thread, so the threads wait for each other at the end of each block; on the same search at 8 threads, with the blastna and packing changes, 208 to 145 MiB at 1.13 times the time; [`docs/agents/diagnostics.md`](docs/agents/diagnostics.md)).
- Added `blastp -db NAME`: BLASTP searches an NCBI BLAST protein database (the files of makeblastdb without `-parse_seqids`, or of `LOSAT makedb`; format versions 4 and 5, several volumes, alias files with `TITLE` and `DBLIST`, and with `NSEQ` and `LENGTH` when they equal the sums of the listed databases, as `blastdb_aliastool -dblist` writes them; the database is found along NCBI's search path, `BLASTDB` and `.ncbirc`) and gives the output of NCBI BLAST+ 2.17.0 `blastp -db NAME -num_threads 1` for outfmt 0, 6 and 7, the same at every `-num_threads`. The database is read in blocks, so the search holds its index (12 bytes per sequence) but not its sequences. `-db` cannot be combined with `-subject` or `-subject_loc`. Rejected explicitly: a database sequence that holds a gap character (`-`), a sequence with more than one definition line, and what the database reader rejects (parsed Seq-ids, id and taxonomy filters, several databases in one name). Added `blastp -dbsize N` (NCBI's effective database length) for `-db` and `-subject` searches; `-searchsp` stays unsupported.
- Added `LOSAT makedb -in FASTA -dbtype prot|nucl -out NAME [-title T] [-max_file_sz S]`: it writes an NCBI BLAST database (format version 4, as `makeblastdb -blastdb_version 4` without `-parse_seqids`) that NCBI BLAST+ 2.17.0 searches with the same output as on makeblastdb's own database. The sequence and header files are the same bytes as makeblastdb's and the index file differs only in the creation date. `-parse_seqids`, mask and taxonomy options and `-blastdb_version 5` are rejected by name. LOSAT's programs do not search a database yet (`-db` stays a rejection).
- Fixed when `blastp` ends the composition-based redo of a query early. NCBI BLAST+ ends the remaining matches of a query only when the hit lists of all queries of its query batch (10,000 residues of queries) are full. LOSAT looked at the query's own hit list alone with two or more threads and two or more queries that have hits (a query whose hit list was full got the result of searching it alone: two queries against Swiss-Prot differed in 42 of 624 rows), and at the hit lists of all queries of the input, not of the batch, with one thread or one query that has hits. With `-max_target_seqs` 500 either case needs more than 500 significant subjects for one query. The result now follows NCBI's batches at every thread count.
- Fixed the order of two `blastp` HSPs of one query-subject pair whose scores tie only after the composition-based redo rounds them. NCBI BLAST+ sorts each subject's HSPs by E-value when it makes the alignments it reports, and E-values below 1.0e-180 count as equal there, so such a pair is ordered by its rounded score and then by subject start; LOSAT kept the order of the unrounded scores. In 64 OrthoFinder-style jobs (about 600,000 rows) two pairs differed, in order only.
- The exact performance paths of the 2026-10 performance work (57 `LOSAT_X_*` switches of the "strict set") are on by default in every program, natively and in WebAssembly. Each of them gives the reference result by construction, so reports do not change. `LOSAT_X_DEFAULT=0` runs the previous paths, and `LOSAT_X_<NAME>=0` turns one switch off ([`docs/agents/diagnostics.md`](docs/agents/diagnostics.md), "Performance switches"). The Web reactors receive no environment and always run the default.
- Costs of the default: megablast keeps one byte per base of a subject while it is searched, and tblastn keeps up to 256 MiB of subject translations for a search of four or more query batches (20,000 query residues per batch); a search of up to three batches keeps none. TBLASTX builds only the lookup tables its seed stage scans, frees them before the HSP list of the last subject of a query batch is merged and linked, and sorts and links the HSP list of a subject without a second copy; on a 0.66 Mb by 0.61 Mb pair its peak memory is 163 MiB at 8 threads and 111 MiB at 1 thread, below the previous paths (320 and 249 MiB in the same measurement). On targets other than x86_64 and WebAssembly no vector X-drop kernel exists, and the scalar code runs there.
- `tblastn` with two or more threads on many subjects hands each thread a chunk of consecutive subjects at a time instead of one subject, cut by residues as NCBI's database reader cuts them for its search threads: at most `min(2^30, F) / (4 * threads) + 1` bases, at least one subject, where F is a quarter of the subjects' bases (the `.nsq` file `makeblastdb` would write), so a long subject is a chunk of its own (`LOSAT_X_TBNOIDCHUNK`, one of the switches above). On 28,036 16S subjects (40.6 Mb) at 8 threads a 55-protein search took a median of 1.35 s against 2.81 s without it, and a one-protein search 0.61 s against 1.50 s; 20 zebrafish proteins against the fly genome (1,870 records, the chromosome arms first) took 7.0 s against 6.8 s (four rounds on a loaded machine). Reports and peak memory are those of the search without it.
- Megablast's preliminary greedy alignment runs the fused loop by default (`LOSAT_X_GREEDYFUSE`, one of the switches above). Measured in #171 on 100 16S queries against RefSeq 16S (28,036 subjects), one thread, on the workstation: wall time 0.74-0.81 of the reference; NCBI 2.17.0 `-db` over LOSAT 1.24 -> 1.63; the same bytes.
- `tblastx` with two or more threads sorts the index orders of the HSP list of a subject faster (`LOSAT_X_LINKSORT`, one of the switches above): the linking call sorts its output order once where it sorted twice, and a long index sort runs as a stable parallel sort on the search pool, with the same order as before. At 8 threads the whole search took x0.926 of the time on the 0.66 Mb by 0.61 Mb pair (AP027131 x AP027133, genetic code 4) and x0.956 on a genome against itself (NZ_CP006932); at 1 thread the difference is within the noise. Reports and peak memory are unchanged.
- On aarch64, `blastp` and `tblastn` solve the Newton problems of the composition adjustment eight per round instead of four (`LOSAT_X_NEWTONLANES8`, one of the switches above); each problem keeps its operations, so reports do not change. Measured on the GitHub runners with bench5's blastp_wssv / tblastn_small at one thread: wall time 0.98 / 0.96 of four lanes on Linux arm64 (Neoverse-N2) and 0.97 / 0.89 on macOS arm64. x86-64 and WebAssembly keep four lanes.
- `tblastn` does less work per subject (`LOSAT_X_TBNSTATE` and `LOSAT_X_TBNXLATE`, two of the switches above): a search thread keeps the scan state of its word finder and gapped alignment from one subject to the next, as NCBI's search threads do, instead of making it for each subject and clearing its diagonal table for each piece of a subject (it keeps one state, about 1 MB for 84,000 query residues, until it ends or its next tblastn search), and the six frames of a subject are read from codon tables, as NCBI translates the compressed subject. Reports do not change. On the workstation at 8 threads (alternating rounds; the same reports; peak memory equal or lower): 55 proteins against 28,036 16S sequences (40.6 Mb) 1.07 -> 0.85 s (x0.79; at one thread x0.70), zebrafish proteins against the fly genome 15.8 -> 13.7 s (x0.86), and on a build before #191 fly proteins against the zebrafish transcriptome x0.76, against the human transcriptome x0.74 and against the zebrafish genome x0.87. The 16S search then takes 0.84-0.96 of the time of NCBI BLAST+ 2.17.0 with `-db` at 1, 8, 16 and 32 threads.
- `tblastn` with two or more threads on many subjects no longer waits between entries of chunks and searches the pieces of a long subject on all threads (`LOSAT_X_TBNOIDNEXT` and `LOSAT_X_TBNOIDUNITS`, two of the switches above): a thread takes the next chunk of subjects when it is free, as NCBI's search threads ask the database for the next chunk, and the (frame, piece) units of a subject longer than a chunk's budget (a chromosome) are searched by the threads that have no chunk left, with the results entered in NCBI's order. Reports do not change. On the workstation (alternating rounds; the same reports and CPU time): zebrafish proteins against the fly genome at 8 threads 13.7 -> 9.7 s (x0.71), fly proteins against the zebrafish genome x0.89, against the human genome at 16 threads 272.6 -> 265.4 s (x0.97), against 28,036 16S sequences and the zebrafish transcriptome x1.00 and x1.01.
- `tblastx` links the groups of a subject's HSP list where they lie in the list (`LOSAT_X_LINKSLICES`, one of the switches above): the linking call no longer cuts the sorted list into one list per group and copies the linked groups into a new list, so the list does not exist twice. At 8 threads the whole search took x0.900 of the time on the 0.66 Mb by 0.61 Mb pair (AP027131 x AP027133, genetic code 4), x0.948 on AP027131 against 200 contigs and x0.988 on a genome against itself (NZ_CP006932); at 1 thread the difference is within the noise. Max RSS on NZ_CP006932 against itself went from 141 to 130 MiB at 1 thread and from 235 to 215 MiB at 8 threads; on the other two it is unchanged (on the pair the search peaks in its seed stage). Reports are unchanged.
- `blastn` keeps one byte per subject base less during a search with many subjects: the traceback makes the uncompressed (blastna) letters of the subject it aligns from its record, as NCBI BLAST+ fetches them per subject in its traceback, instead of keeping them for every subject from the start. Reports do not change. Megablast of 100 16S queries against 28,036 16S sequences (40.6 Mb): peak memory 236 to 197 MiB at one thread and 246 to 206 MiB at 8 threads; with one query 119 to 79 MiB (same-run measurements). A search against one long subject keeps its peak, since its traceback encodes that subject.
- `blastn` prepares its subjects faster: it packs each subject's letters in one pass, resolving only the ambiguous letters (as before, from NCBI's `CRandom` seeded with the subject length, in the same order), instead of converting and resolving every letter into a second buffer first. The packed letters, and so the reports, do not change. At one thread a megablast search without hits against 28,036 16S sequences took a median of 0.17 s instead of 0.44 s, and a search with one query a median 0.72 of its previous time (8 alternating pairs each).
- `LOSAT_X_PAIRPARDISC=1` (off unless set; not in the strict set): `blastn -task dc-megablast` searches its two-hit seed stage on the search pool when one subject is searched with two or more threads and the query block is longer than 8,000 letters: the pool threads scan strips of the subject and the owner thread folds the word hits into the diagonal hash in the reference order, so reports do not change (`LOSAT_X_PAIRPARDISCSHADOW=1` compares each chunk with the reference). The owner's fold limits the gain beyond 4 threads: on 5,000 D. melanogaster cDNAs against 3 Mb of chromosome 2L, local pairs at load 22-28, wall time with the switch on was 0.49 of off at 4 threads and 0.56 at 8; peak memory +5 % ([`docs/agents/diagnostics.md`](docs/agents/diagnostics.md)).
- `blastp -subject` with two or more threads searches its subjects in runs of consecutive subjects (`LOSAT_X_BPSUBJRUN`, one of the switches above; shadow `LOSAT_X_BPSUBJRUNSHADOW`, opt-in): each run clears its diagonal table once, instead of clearing it for every subject and making a new search scratch for every piece of work, so reports do not change. On the workstation (16 physical cores; medians of alternating pairs; every output hash equal; peak memory equal) `blastp-fast` of the human proteome against the yeast proteome with `-subject` took 0.89 of the time at 16 threads (6 pairs; 0.88 with `LOSAT_X_BPQBLOCK=20000`), 0.90-0.92 at 8 and 0.92 at 4; exact `blastp` 0.998 at 16 and 0.995 at 8; one thread is unchanged. `LOSAT_X_BPSUBJRUN=0` turns it off ([`docs/agents/diagnostics.md`](docs/agents/diagnostics.md)).
- Added the experimental switch `LOSAT_X_BPREDOPAR` (off unless set; not in the strict set; shadow `LOSAT_X_BPREDOPARSHADOW`): with two or more threads, `blastp` redoes the matches of a search's composition-based redo, when it has at least two, in jobs of up to four matches instead of one query per job, and replays the early termination test and the hit list insertions in the order of the one-thread redo, so reports do not change ([`docs/agents/diagnostics.md`](docs/agents/diagnostics.md)).
- `LOSAT_X_QBATCHPAR=1` (off unless set; not in the strict set): `blastn` with `-subject` and two or more threads searches NCBI's query batches side by side ahead of the batch loop, in slots of one or more threads, with a prediction of NCBI's adaptive batch sizes. The loop still reads every batch with NCBI's batch sizes and takes a slot's result only for that same batch, so reports and standard error do not change (`LOSAT_X_QBATCHPARSHADOW=1` compares every batch taken from a slot with the loop's own search; `LOSAT_X_STATS` prints a summary line). Every slot is stopped before anything is written, and no batch planned after one that failed is started. The batches in flight follow a memory budget (`LOSAT_X_QBATCHPARMEM`; by default 96 MiB per thread beyond the first for blastn and 28 MiB for megablast and dc-megablast, so dc-megablast's 5 Mb batches need six threads or more). Off with `-db`, and when the subjects already give every thread work (as many 5 Mb pieces as threads) ([`docs/agents/diagnostics.md`](docs/agents/diagnostics.md)).

## [v0.1.0] - Initial Release Candidate

Initial release candidate for LOSAT as a standalone, pure-Rust reimplementation of NCBI BLAST+ local sequence alignment behavior, designed for direct pairwise FASTA comparisons (`-query` vs `-subject`) with bit-identical output parity and WebAssembly portability.

### Added

- **Supported Programs & Search Tasks**:
  - **`blastn`**: Supports pairwise nucleotide alignment with `megablast` (default, word size 28, affine/linear penalties) and traditional `blastn` (word size 11, match/mismatch 2/-3, gaps 5/2).
  - **`blastp`**: Supports pairwise protein alignment using BLOSUM62 matrix and affine gap penalties (open 11, extend 1).
  - **`tblastx`**: Supports 6-frame translated pairwise nucleotide alignment with full genetic code customization.
- **Bit-Perfect NCBI BLAST+ Parity**: Produces identical alignment boundaries, bit scores, and E-values matching official NCBI BLAST+ (v2.17.0+) across certified pairwise profiles.
- **Standard Output Formats**: Supports canonical tabular output (`-outfmt 6`) and commented tabular (`-outfmt 7`) reporting the standard 12 BLAST fields (`qseqid sseqid pident length mismatch gapopen qstart qend sstart send evalue bitscore`), plus pairwise text alignment (`-outfmt 0`) for `blastp`.
- **Pure-Rust Standalone Runtime**: Zero external C/C++ dependencies or shared libraries. Does not link, embed, wrap, or invoke NCBI BLAST+ binaries at runtime.
- **Direct Pairwise Alignment**: Directly aligns sequences from FASTA files via `-query` and `-subject` without requiring database formatting (`makeblastdb`).
- **WebAssembly & WASI Support**: Compiles to standalone WASI command-line binaries (`wasm32-wasip1`) and multithreaded WASI (`wasm32-wasip1-threads`) for sandboxed CLI and browser-based bioinformatics applications (such as [gbdraw](https://github.com/satoshikawato/gbdraw)).
- **Cross-Platform Native Binaries**: Pre-compiled and verified binaries for Linux (x86_64, aarch64), macOS (Apple Silicon arm64 & Intel x86_64), and Windows (x86_64).
- **Bioconda Distribution**: Officially available on Bioconda as `losat` (`conda install -c bioconda losat`) across Linux and macOS architectures.

### Changed

- User-facing documentation clarifies that NCBI BLAST+ is used strictly as an independent validation oracle during testing, not as a runtime dependency or fallback path.
- Parameter validation fails fast with explicit error messages when encountering unsupported options rather than silently degrading or falling back.
- Wasm documentation clearly distinguishes standalone WASI command builds from experimental browser library APIs.

### Approved Parity Enhancement

- **TBLASTX Subject Genetic Code (`--db-gencode`)**: In local pairwise `-subject` searches, LOSAT explicitly honors non-default `--db-gencode` for translating subject sequences (supporting genetic codes 1–33). This resolves a recognized NCBI BLAST+ limitation where local `-subject` mode defaulted to genetic code 1 regardless of `--db-gencode`. All scoring, statistical calculations, and alignment logic remain strictly identical to NCBI.

### Scope & Known Limitations

- **Database Search**: Pre-formatted BLAST databases (e.g., `.nin`, `.nhr` created by `makeblastdb`) and remote NCBI queries (`-remote`) are outside the v0.1.0 scope; comparisons are strictly pairwise FASTA (`-query` vs `-subject`).
- **Unimplemented Programs**: `blastx` and `tblastn` are not implemented in this release.
- **Discontinuous MegaBLAST**: `dc-megablast` is not yet supported.
- **Library API**: Rust crate library interfaces and embeddable Web/Wasm APIs are currently internal-only; stability is guaranteed at the CLI level.

### Verification Authority

Governed by program certification records in `docs/release/` (`blastn_v0.1.0_certification.md`, `blastp_v0.1.0_certification.md`, `tblastx_v0.1.0_certification.md`) and the pure-Rust runtime authority in `docs/release/pure_rust_runtime_v0.1.0_certification.md`.

## Findings

### A-1 (low) BLASTN: a non-UTF-8 byte in a -query_loc / -subject_loc value is a clap parser error instead of NCBI's ordinary range error
- Command: `blastn -query q12k.fa -subject s25k.fa -query_loc $'\xff'` (scratch_A/q12k.fa = LvMJNV[20000:32000], s25k.fa = mutated copy of LvMJNV[15000:40000]); same with `-subject_loc $'\xff'`.
- NCBI 2.17.0: stdout empty, stderr `BLAST engine error: Invalid specification of query location (Format: start-stop)` exit 3 (ParseSequenceRange: one token => the "(Format: start-stop)" CBlastException, blast_input_aux.cpp:145-179 as ported in S11.diff seq_range.rs). The `-subject_loc` twin: "... subject location ...", exit 3.
- LOSAT-head: stderr `error: invalid UTF-8 was detected in one or more arguments ... Usage: LOSAT-head blastn [OPTIONS]`, exit 2.
- Also `-query_loc $'1-\xff'` / `$'\xff-5'` (an R1 input: NStr::StringToInt cannot convert, NCBI exit 255): LOSAT exit 2 with the clap text instead of the R1 message "... cannot convert to an int ...; this is not supported by LOSAT's BLASTN" with exit 1. (Valid-UTF-8 non-ASCII such as `1é-5` and full-width digits do reach the R1 message correctly.)
- NCBI USAGE is not involved (NCBI accepts any bytes for an eString key), so this is not the approved parser-syntax-error class for the first form; the R1 form is at least a different message/exit than R1 documents.
- LOSAT location: `LOSAT/src/algorithm/blastn/args.rs:236-255` (`query_loc`/`subject_loc: Option<String>`; same in blastp/tblastn/tblastx args.rs) - clap decodes the value as UTF-8 before `parse_sequence_range` (seq_range.rs) can apply NCBI's token logic. Would need an OsString-typed arg.
- Severity: low (byte values that are not UTF-8 in a range argument).

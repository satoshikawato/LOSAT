# LOSAT Webアプリ：実装デザイン構想

**版：設計レビュー用 v0.1／2026-09-27**

## 0. 本書の位置付け

対象は、手元の配列をブラウザ内のLOSATで比較・検索する、インストール不要のWebアプリである。研究データを検索サーバーへ送らず、同じSubjectを保持して反復検索し、結果確認・配列回収・手動書き出しまで行う。

本書はユーザー回答Q001–Q060、追加回答R01–R30、および最新の一時ファイル方針を基にする。**要求として確定した事項と、それを実現するための設計提案を区別する。** モジュール名、内部API、保存形式、スレッド方式、技術スタックは、一括レビュー対象の提案であり、実装済みという意味ではない。

現行リポジトリのコード監査、対応プログラム・出力形式の実装確認、NCBI Web画面との全項目対応、性能測定は本書では実施していない。ブラウザの保存・Worker・オフライン更新・GA4に関する技術的前提は、末尾の公式技術文書を確認した。

要求の解釈では、**最新の明示決定 → R回答 → R回答で変更されていないQ回答**の順に扱う。以前のAgent案は背景資料であり、採用されなかった機能を再導入する根拠にはしない。

### 最新決定 T01：計算用一時ファイル

エンコード済み配列、翻訳・マスキング等の派生データ、元FASTAの位置・長さ・ID対応等の索引、ヒット・アラインメント結果は、**端末内の一時ファイルとして自動作成してよい。利用者への事前確認は不要**。

これは旧Q043「使用前に確認」を更新する。次回利用のための研究データ・検索履歴の自動保存／自動復元は行わない。保存用の結果・配列・設定・セッションファイルは利用者の明示操作で書き出す。一時領域の具体的な選択・容量管理・削除・異常終了後の回収方法は設計レビュー対象である。

## 1. 設計の中心

**「FASTA文字列を毎回Wasmへ送り、検索終了後に巨大な結果文字列を受け取るだけの画面」ではなく、「一度開いた検索対象を再利用し、その作業中のデータを管理するローカル検索アプリ」とする。**

中核は次の分離である。

| 分離するもの | 設計上の意味 |
|---|---|
| 元入力と計算用の表現 | 元配列を忠実に抽出できることと、計算用のエンコード・マスキングを両立する |
| 作業状態と計算Worker | Workerを停止・再生成しても、Subject・過去の結果・候補を失わない |
| 編集中の設定と実行時の記録 | 次のジョブの編集で、実行中・過去の検索条件を変えない |
| 一時保持と保存用ファイル | 自動一時ファイルは許可するが、次回自動復元はしない |
| 検索結果と表示用の加工 | フィルター・ソート・描画の都合で元結果の意味を変えない |
| 互換出力とアプリ独自出力 | NCBI比較対象のテキストと、CSV・独自JSON等の加工物を区別する |

この分離を満たす小さなアプリケーション層を置く。サービスの分割配備、マイクロサービス、公開SDK、大規模なプラグイン基盤は要求しない。

根拠：Q037–Q040、Q048、Q053–Q056、R01–R03、R19、R21、R29–R30、T01。

### 2.1 初期の正式公開に必要な範囲

出典：Q001–Q056、R02–R21、R24、R26、R28。五つの機能が現行コードで完成しているとは認定しない。

### 2.2 後続・対象外・未決を混ぜない

**後続**：PWAとしての利用、複数レコードを一画面にまとめるドットプロット、次のqueryにする操作、利用者が指定する逆相補化・表示方向変更、環状境界をまたぐ抽出、短いquery向け特別対応、高度なpause/resume、初回・更新時の小さな自動試験。

**対象外**：巨大公開DBの配信・検索、全ゲノム自動注釈、多重アラインメント、系統解析、クラウド同期、高度な図編集、GenBank／GFF3入力、圧縮FASTAの直接入力、Query／Subject入替ボタン、gbdraw専用連携、自己ホスト用パッケージ。同じUIのネイティブ版は今回考慮しない。

**採否・時期が残るもの**：SVG／PNG、リボン等の簡易トラック、追加比較行列・all-vs-all専用操作、外部API／SDK、実行差分比較、追加表示調整など。GA4は採用指定があるが、計測範囲・同意・配置は未確定。元核酸文字列の併記は採用済みだが時期が未記入。「BLASTで見える値はすべて」というフィルター要求は、具体表と採用時期をレビューする。

**開発を段階に分けても、初期必須を省いたものを正式公開しない。** Q015の公開方針を維持する。

## 3. 利用者の一連の操作

### 3.1 最初の検索

ページを開くと検索画面が現れる。アカウント、DB登録、プロジェクト名、PWAインストールは要求しない。programと入力種別を選び、QueryとSubjectを貼り付けるかローカルFASTAを開く。

大きなファイルは全文をtextareaへ流し込まず、ファイル名・配列数・総長・種別・先頭プレビュー・レコード一覧・警告を見せる。問題レコードは利用者が明示的に除外できる。入力規模の確認後、Run locallyで実行する。

処理中は準備／検索／結果整理、完了query数、経過時間を示す。進捗率・残り時間は測定できる場合だけ出す。入力内容を推測してprogramを自動変更しない。

### 3.2 反復検索

Subjectを開いたままQueryを変更する。同じSubjectの入力参照・索引・エンコード・有効な前処理は再利用する。過去の結果と候補は別に保持し、新しい検索のために上書きしない。

実行中の条件は固定されるが、次のジョブのQueryと条件は編集できる。「Add to queue」でその時点の入力と条件を固定して登録する。フォームから古い入力を外しても、既にキューに入ったジョブが別の入力に差し替わらない。

### 3.3 結果確認と回収

正常完了後、queryを選び、Subject一覧から候補を選ぶ。HSP、ドットプロット、アラインメントを確認し、必要に応じて候補トレイに登録する。元配列区間、左右の周辺、全長、ギャップ付きアラインメントを、意味を区別して取得する。

保存用ファイルはDownload／Exportを押した場合に作る。アプリの次回起動時に作業を勝手に復元しない。セッションファイルの読み込みは利用者がファイルを選ぶ明示操作であり、自動永続保存とは別である。

### 3.4 画面の骨格案

```text
LOSAT                            Local processing / Runtime / Help
[ Search ] [ Results ]           [ Queue ] [ Candidates ]

Search
  [five program tabs: 表示名は別途確定]
  Query                          Subject
  Paste / Open local file        Paste / Open local files
  Records / Regions              Combined | Separate searches
  Program parameters             Subject retained
  Threads: Auto / number
  [ Run locally ] [ Add to queue ]

Results
  Run selector / Query selector
  [ Hits ] [ Dotplot ] [ Alignments ] [ Run details ]
  Subject list → HSP selection → aligned sequences
  [ Extract ] [ Add to candidates ] [ Export ]
```

Queue・Candidatesは補助パネルの提案であり、第三・第四の大きな作業モードを要求するものではない。モバイルは同じ機能関係を保って縦に配置する。

根拠：Q006–Q007、Q021、Q027–Q040、Q050–Q056、R02–R04、R06、R09、R11、R15–R18。

## 4. 全体アーキテクチャ案

```text
静的配信：アプリ / Worker / Wasm / 例題 / 検証情報
                         │
                         ▼
UI + Application coordinator（main thread：軽い状態・操作）
  ├─ SearchDraft / RunSnapshot / Queue
  ├─ ViewState / CandidateTray
  ├─ DatasetService ──────────┐
  ├─ ResultService ───────────┤
  ├─ ExportService ───────────┤
  └─ EngineSupervisor        │
         │                   ▼
         │             Data worker
         │               ├─ 元File参照 / 範囲読み出し
         │               ├─ 索引 / 資源・参照管理
         │               ├─ Memory working store
         │               └─ OPFS temporary store
         ▼                   ▲
   Compute worker(s) ─────────┘
     ├─ LOSAT Web adapter
     ├─ 一つの管理された実行資源枠
     ├─ LOSAT検索コア
     └─ HSP・詳細データ / 互換formatter

Service Worker：アプリ資産のキャッシュと更新だけ
GA4：研究データ処理とは切り離した計測経路（配置は承認待ち）
```

DatasetService等は責務名であり、各一つのWorkerやデータベースを必ず作る意味ではない。最初の物理構成は、UI、データI/O用Worker、計算用Workerとその計算プールを基本案とする。

**計算Workerに、Subject・完了結果・候補の唯一のコピーを持たせない。** 通常の検索ではWasmと前処理を維持するが、異常時に計算Workerを失ってもアプリ側の作業参照は残る。検索コアの数値処理・アラインメントロジックをUI側へ再実装しない。

Service Workerを検索の実行主体や、タブ終了後も解析し続ける仕組みには使わない。

## 5. データモデルと寿命

| オブジェクト案 | 内容 | 寿命・所有関係 |
|---|---|---|
| SessionContext | 今の作業を識別するランダムID、保持物の参照関係 | 新しい作業で新規作成。次回起動時の研究履歴をロードする入口にしない |
| SourceRef | 元File参照または貼付入力への参照 | 検索・結果・候補・書き出しが必要とする間保持 |
| DatasetRevision | source、レコード順、内部ID、種別、除外、領域選択 | 不変。編集は新しいrevisionを作る |
| PreparedSubject | 索引・エンコード・該当する前処理 | 条件とrevisionが適合する間再利用 |
| SearchDraft | 次に行う入力と条件 | 編集可能 |
| RunSnapshot | 固定入力revision、対象集合、正規化した検索条件、遺伝暗号表、選択したapp／engine版、要求資源 | キュー登録時に固定。再実行は新しいrun |
| RunRecord | RunSnapshotへの参照、開始時に決まる実効実行経路・スレッド構成、処理時間、終了状態 | 実測・確定した情報を追記する。要求値や検索条件を後から上書きしない |
| RunState | 待機・実行・整理・完了・取消・失敗、進捗 | 一回のrunに限定 |
| ResultSet | HSP索引、詳細参照、統計、元出力用情報、実行記録 | runの完了後、明示削除／作業終了まで |
| ViewState | 選択、列、表示フィルター、ソート、表示範囲 | 元ResultSetを書き換えない |
| Candidate | 元run・レコード・HSPへの参照、抽出条件、メモ | 別検索・取消に巻き込まれず作業中に保持 |

キュー登録時には入力と検索条件を固定するが、実際に起動できたスレッド数やフォールバック経路まで未測定のまま確定しない。要求値はRunSnapshot、実際の実行情報はRunRecordで区別し、両者をそのrunの記録として保持する。

メモ等の利用者状態を一時ファイル許可に乗じて次回復元用に保存しない。大量の計算データを一時保存することと、作業履歴を自動保存することを分ける。

索引・詳細ブロックのファイル名には入力名を埋め込まず、内部トークンを使う。索引の内容には元ヘッダー等が入るため、一時ファイルも研究データとして扱う。

削除操作でDatasetを外すときは、関連結果を残すかも選択できるようにする。残した結果に元配列がなければ、抽出不能を明示する。黙って別の同名ファイルへ参照を付け替えない。

## 6. 入力・索引・部分読み出し

### 6.1 元FASTAを上書きしない

通常のファイル入力では元Fileを読み取り専用で参照し、解析に必要な索引と計算用データだけを作る。元FASTAを作業領域へ丸ごと複製することを標準動作にしない。貼付入力は元文字列・原配列を保てる参照を作り、ファイル入力と同じ論理インターフェースで扱う。

計算用に小文字・マスク・曖昧文字等を変換した表現から、元配列を無条件に逆算しない。抽出には元ソース、または原配列を忠実に復元できる表現を使う。元の貼付文字列を保持することと、巨大な変換済み文字列を何重にも作ることは別である。

### 6.2 索引に持つ情報

ファイル内のレコード位置、配列開始位置、配列長、元ヘッダーと内部ID、配列座標からファイルoffsetへの対応を持つ。FASTAは可変折り返し・LF／CRLF・許容空白・非ASCIIヘッダーも試験する。固定行長を確認せずに一定幅の算式だけで区間を切り出さない。

巨大レコードでは途中から読めるチェックポイントを持つ案とする。総長・ファイルoffsetは64-bitの値として管理し、Wasmの一時バッファ内offsetと区別する。JavaScriptへ渡す際の整数精度・変換可能範囲も検査する。

同名IDは統合しない。内容、除外レコード、領域、種別の変更をrevisionとして追跡する。ハッシュは再読込時の照合に用いる候補であり、ファイル名・サイズだけで一致としない。

### 6.3 アプリと検索コアの境界

SequenceProvider相当の境界を設け、「レコードの情報」「必要区間の原配列」「必要な計算表現」を取得する。メモリ型と一時ファイル型で検索の意味を変えない。

ホスト側の非同期I/Oと、同期的に走るWasm関数の受け渡しは明示的な契約にする。第一候補は、有限サイズの入力バッチを準備し、検索コアが論理的な一つのrunを維持したまま処理を進める方式。単に巨大な同期関数へpostMessageを送れば途中でI/O要求や取消を処理できる、と仮定しない。

一レコードより細かい読み出しが必要な場合は、コアが必要区間を取得できる実装を検討する。UIだけで配列を切り刻み、独立検索の結果を連結する方式へ置き換えない。

## 7. メモリ＋一時ファイルの階層管理

### 7.1 保存先案

小さなメタデータと表示中データはメモリ、計算用の大きなブロックと大量結果は必要に応じてOPFSへ置く。元ファイルはFile参照から読む。MemoryWorkingStoreとOpfsWorkingStoreを同じ作業用ブロックI/O契約の二実装とする。

OPFSはブラウザのorigin専用領域で、通常のファイル選択・権限確認なしに利用でき、Worker向けのファイルI/Oも提供される。ただしディスクに保持される仕組みであり、「一時」というラベルだけでタブ終了時に必ず消えるものではない。[W1]

**一時ファイル作成前のアプリ確認ダイアログは出さない。** 使用量・解放操作は非モーダルな状態表示にする。OPFSが利用不能な環境ではメモリ型で可能な範囲を処理する。実際の機能をprobeし、ブラウザ名だけで経路を決めない。

作業領域例。名称は仮であり、一般公開形式ではない。

```text
tmp/<session-token>/
  owner.meta                 # 清掃・所有判定用。研究履歴の自動復元には使わない
  datasets/<revision-token>/
    index.blocks
    encoded.blocks
    derived/<cache-key>/...
  runs/<run-token>/
    staging/summary.blocks
    staging/detail.blocks
    committed/...
```

OPFSの同期アクセスハンドルは専用Workerで使うAPIであり、ファイルのアクセスモード・ロックの契約も考慮する。[W2] 最初はデータWorkerを書き込みの窓口にし、compute workerが同じファイルを競合して更新する構成を避ける。必要な非同期要求と書き込みACKを定義する。

### 7.2 一時データの削除案

| 出来事 | データの扱い |
|---|---|
| Queryだけ変更 | Subjectと適合する前処理を保持 |
| 正常完了 | 結果を作業中の確定結果として保持。次回復元用の保存ではない |
| 取消・失敗 | 当該runのstagingを破棄。Subjectと以前の確定結果は維持 |
| 前処理条件変更 | 不適合な派生データを再生成。参照中の別runを壊さない |
| 容量圧迫 | まず再生成可能で未使用のキャッシュを解放。保持中の確定結果を黙って捨てない |
| 明示的な作業終了・全消去 | 対象作業の計算を停止してから参照を閉じ、一時領域を削除 |
| タブ／ブラウザ強制終了 | 削除完了を前提にしない。次回起動時に所有者のない残存領域を回収する案 |

GCの生存参照は、実行中run、キュー、過去結果、候補、表示読込、書き出し処理まで数える。書き出し途中の参照を解放してはいけない。

複数タブが同じoriginを使う場合、セッションごとの名前空間と所有ロックを使う。Web Locksは同一originのタブ／Worker間の協調に使える。[W3] 残存回収では、停止・バックグラウンド化されたタブを最終アクセス時刻だけで死んだと判定しない。所有者不在を安全に判定できない環境では、別タブのデータを自動削除するより回収を保留する。更新後のアプリが旧版で稼働中のタブを清掃しないことも試験する。

**次回起動時に残存データを見つけても、前回の研究履歴として自動表示・自動再開しない。** 不要領域の清掃と履歴復元は別である。削除はアプリ管理領域の論理削除であり、強制終了直後の完全消去やOS・SSD上の復元不能性は約束しない。

### 7.3 容量不足

アプリ自身の管理バイト数とブラウザが報告する容量見積りを区別する。Storage APIのestimateは確保保証ではなく、書き込みはQuotaExceededError等で失敗し得る。[W4]

未使用キャッシュの解放後、メモリ経路へ移って同じ検索を完了できる場合は続行する。必要情報を保持できない場合は理由付きで失敗にし、過去の完了結果を残す。「保存できない場合も可能なら実行する」を「資源が不足しても必ず完了する」と読み替えない。

## 8. 五つのprogramを支える共通基盤

| Program ID | Query | Subject | 派生処理の主な対象 |
|---|---|---|---|
| BLASTN | 核酸 | 核酸 | 核酸エンコード、taskに対応する処理 |
| BLASTP | タンパク質 | タンパク質 | タンパク質エンコード、対応するマスク等 |
| BLASTX | 核酸 | タンパク質 | query側の翻訳・frame・遺伝暗号表 |
| TBLASTN | タンパク質 | 核酸 | subject側の翻訳・frame・遺伝暗号表 |
| TBLASTX | 核酸 | 核酸 | 両側の翻訳・frame・遺伝暗号表 |

この表は入力関係の整理であり、現在の実装状態表ではない。ユーザー向けLOSAT系の表示名は別途統一し、原回答の綴りを黙って正式名へ置き換えない。

元データは核酸／タンパク質の二種類を基本とし、五programのために元FASTAを五重に保存しない。programごとに必要な前処理と結果解釈は明示的に実装する。

### 8.1 キャッシュキー案

```text
source revision
+ 対象レコード・検索範囲
+ 計算表現の種類／スキーマ
+ 関係するprogram・task・入力側の役割
+ 関係する遺伝暗号表・mask等の条件
+ 生成に使ったengine build
```

キーは、その派生物の値を決める条件で構成する。query変更だけで共通のSubject索引まで捨てない。一方で、遺伝暗号表が変わったのに翻訳キャッシュを使い回さない。query依存の構造を、Subjectだけで決まるキャッシュだと誤認しない。

全ゲノムの全frameの翻訳文字列を常に事前生成する設計にはせず、必要な範囲・再利用効果・容量を見て段階的に生成する案とする。再利用の効果は、入力・前処理の短縮と検索本体の短縮を別々に測る。

### 8.2 大容量検索で変えてはいけない意味

Combinedモードは選択ファイル群を一つの論理Subject集合として扱う。Separateモードは独立した検索対象・統計・結果を持つ。Separateを個別RunSnapshotへ展開してキューに積む構成を提案する。この場合、R03の結果確定単位は各runとなる。一括依頼全体の原子的な取消操作まで必要かは、画面案のレビュー事項として分ける。

I/Oバッチを変えても、論理的な検索対象、統計、候補選別、最終順位は変えない。特にSubjectを独立検索に分割して局所E-value・局所top-Nを結合しただけのものを、Combined結果として扱わない。

巨大な一レコードでは、境界をまたぐHSP、正逆方向、翻訳frame、延長、候補選別を保つ必要がある。任意の固定長や固定オーバーラップで切れば同等になるとは仮定しない。コア側の範囲供給・継続処理を実装するか、その入力構造を未検証／実行不能として説明する。初期の代表的データ規模は実測して有限に定め、上限値を本書で捏造しない。

## 9. 並列実行・進捗・取消

### 9.1 本線と代替経路の提案

**本線候補は、永続的なEngineRuntimeと一つの管理された共有メモリ型計算プール。代替は、同じアプリ契約を満たす単一Worker／非共有メモリ経路。** 実装済み・検証済み範囲を調べて、五programの比較試験と性能測定で採否を決める。

共有メモリを使う経路はsecure contextとcross-origin isolationを要するため、配信ヘッダーと実行時の確認を含めて設計する。[W5] 初期配信の候補はHTTPS、COOP: same-origin、COEP: require-corpを設定できる静的ホスト。ホスティング業者の契約は本書で決定しない。

独立した直列Wasmを複数queryに配る方式は比較候補に残すが、最初から第三の正式経路として必須化しない。query複数本での並列化だけを、単一queryの高速化を達成した証拠にはしない。Subject複製と全スレッドを使うエンジンの多重起動を避ける。

要求スレッド数、構築されたプール数、実際の実行経路を区別する。AutoはCPUの情報だけでなく作業バッファ・Subjectの保持・I/Oを考慮する。「プールにN本ある」と「常時N本がCPUを使用している」は別である。利用不能時は理由を示して検証済み代替へ切り替える。

### 9.2 メモリ予算

```text
ピーク使用量 ≒
  入力・索引のメタデータ
  + 現在扱う配列／計算ブロック
  + queryに依存する検索用構造
  + 各計算スレッドの作業バッファ
  + 再利用キャッシュ
  + 結果・I/Oの待機バッファ
  + UIに取り出した表示データ
```

ファイルの総容量とWasm内の必要容量は別に測る。Wasm32のポインター範囲と、64-bitの元ファイルoffsetも別である。[W6] 一時ディスクはこの全式を無制限に小さくする機能ではない。巨大query、巨大単一Subject、多数レコード、大量HSPを別々にベンチマークする。

### 9.3 状態機械と仮結果

```text
Queued → Preparing → Running → Finalizing → Completed
                     │            │
                     ├─ CancelRequested → Cancelled
                     └──────────────────→ Failed
```

完了queryのHSP・詳細をstagingへ書き、そのquery分が整合して読める段階で仮表示する。全run成功と必要データの確定を確認してから、結果の公開状態をCompletedへ切り替える。これは作業中の論理コミットであり、次回用の永続保存ではない。

取消または失敗でstagingを破棄する案とする。仮表示からの候補登録・配列コピー／抽出・ExportはUIだけでなくアプリAPI側でも拒否する。全結果が来る前に画面だけCompletedにしない。

イベントにはrun ID、dataset revision、runtime generationを付ける。取消後に遅れて届いた完了イベントや、Worker再作成前のイベントを受け入れない。キャンセル受付とコミットの競合はcoordinatorで直列化する。

### 9.4 実際に停止させる

共有メモリ経路は協調取消フラグを検索・翻訳・延長・結果確定の処理点で確認する。非共有メモリ経路は制御を返せる処理単位を設計し、取消要求に応じられない場合は計算Workerを終了する。

Worker.terminate()は処理の完了や後始末を待たず終了させるため、正常終了時のcleanupだけには依存しない。[W7] Supervisorは関連する計算プールの停止も確認し、旧世代の結果を書かせない。データWorkerは保持し、元File・確定済み結果・候補を残す。強制終了で失ったWasm内の計算キャッシュは再作成してよい。

Wake Lockの利用選択、終了前の注意、スリープ／バックグラウンド化の注意、復帰時の状態確認は初期対象。高度な計算チェックポイント再開は後続であり、「タブを閉じても検索が続く」とは説明しない。

## 10. 結果契約：構造化情報と互換テキスト

### 10.1 同じ検索結果から二つの表現を生成する

推奨案は、検索コアが確定した一つの結果を、二つのアダプターへ渡す構成である。

```text
LOSATの実際の検索結果
  ├─ 互換formatter → outfmt 0 / 6 / 7
  └─ Web adapter   → HSP summary / alignment detail / provenance
                           ├─ 表・図・詳細
                           ├─ 抽出計画・候補
                           └─ CSV / app JSON / report / session
```

内部形式を標準12列TSVだけにしない。詳細には、実際のaligned residues、gap／edit情報、frame、元座標、必要なmask情報を得る。検索結果と異なる再アラインメントを行い、同じ結果として表示しない。

具体的な契約は構造化バッチを第一候補とする。十分な詳細を持つ検証済みテキストを経由するアダプターも移行時に比較可能だが、同じ検索を出力形式ごとに何度も実行する最終構成にはしない。既存CLIの出力を壊さずにWebアダプターを追加する。

### 10.2 大量結果に対応する配置

HSPの小さな要約と、長い詳細アラインメントを分離する。要約はquery／Subject単位の索引を持ち、詳細は必要時に一時領域から取得する。遅延取得は検索のやり直しではなく、同じrunが生成した情報の読み出しである。

UIへ巨大なHSPオブジェクト配列を一括転送しない。有限サイズの結果バッチを送り、受け側が処理しきれないときは送信を抑える。図用の座標、表のページ、選択HSPの詳細だけを取り出す。

元formatterに必要な精度と出力順を保つ。UIの丸めた浮動小数や並べ替え済み行から元出力を復元しない。表示用指標とエンジン原値を区別し、ゼロ表示や同点順序を含め比較試験へ入れる。

### 10.3 検証表示

検証バッジはengine build、program／task、設定範囲、実行経路、比較したNCBI条件、試験記録に結び付ける。CSV・独自JSON・選択結果等の加工物へ、無条件に「NCBIとバイト一致」のラベルを継承しない。

既知の例外は限定された条件と根拠を明記する。出力全体を都合よく正規化して差異を隠さない。研究者の任意入力をその場でNCBI実行と比較したような表現はしない。

## 11. 表・図・アラインメント・抽出の設計

### 11.1 共通の選択状態

Run、query、Subject、HSPの内部IDを選択の中心にする。表の行番号・DOM要素・非一意なFASTAヘッダーを、抽出対象の識別子に使わない。表示フィルター変更前に開始した詳細読み込みが後から返ってきても、別のHSPへ内容を差し込まない。

結果画面はSubject一覧を入口にする。二配列ドットプロットは、選択したqueryとSubjectのペアを表示する。複数配列を同じ軸上に連結して描く機能は後続であり、初期の複数query／Subject受付と混同しない。

ドットプロットはHSP等の検索結果を表示する案であり、未採用の別の全対全配列計算を裏で追加しない。翻訳検索でも軸が核酸座標かアミノ酸座標かを明示し、frameと向きを保持する。

Canvas等の必要範囲描画と仮想化一覧を候補とする。集約表示を使う場合の粒度と表示はレビューし、数値・詳細結果を削る許可にしない。画像のSVG／PNG書き出しは未決のまま残す。

### 11.2 パラメーター・指標の対応表

NCBI Webに準じる入力項目、初期値、列、coverage・identity等を、固定した参照画面／条件と対応付ける。対応表には名称、単位、対象program、算出主体、集約単位、出典、LOSAT実装の状態を持たせる。

「BLASTで見える値はすべて」は、存在しない情報を推測して列を埋める要求ではない。未対応項目は通常画面に出さず、必要な初期項目が欠けるなら実装・検証課題として残す。

検索条件はRunSnapshot、表示フィルターはViewStateに属する。再検索と表示更新は別操作を維持する。表示0件、ヒットなし、未完了、失敗、結果数制限を区別する。設定上限へ到達しただけで、未取得ヒットが必ず存在すると断定しない。

### 11.3 座標・翻訳・元配列

内部では範囲・向き・単位を型として区別する。利用者向けの元配列座標は先頭1・両端を含む表記を基本にする。元レコード、検索対象の部分領域、翻訳frame、アラインメント上の位置の変換を一箇所に集め、RustとUIで別々の暗黙の計算を持たせない。

元核酸文字列の併記は採用済みなので、必要な元座標参照を契約に入れる。ただし実装時期は未確定。文字サイズ・行幅・ダークモード等も、未回答を初期必須にしない。

### 11.4 抽出の意味

原配列の抽出は元レコード方向を既定とする。左右flankはその座標軸上で別々に指定し、端部は切り詰めて要求範囲と実際の範囲を記録する。核酸の長さとタンパク質残基数は単位を明示する。

同じSubject上の複数HSPは、各HSPを別配列にする方式と、間の配列を含む一つの連続区間を選べる。未検証のCDS復元やスプライシング推定は行わない。重複・重なりは勝手に統合しない。

**ギャップ付きアラインメント出力は、原配列区間の抽出とは別**である。逆向きヒットのアラインメントは検索で得た向きに忠実に示す。原配列抽出の既定方向に合わせてアラインメントの内容まで反転させない。利用者が原配列をヒット方向へそろえる追加操作は後続とする。

## 12. 出力・セッション・再現性

### 12.1 出力の契約

保存用ファイルは明示操作からのみ作る。抽出・formatter・serializeは共通のWriter契約へ書き込み、メモリへ全体を一括で組み立てることを標準にしない。一時ファイルから最終ダウンロードへ送る経路も用意する案である。

書き出し画面は「元結果全体／フィルター適用後／選択分」を区別する提案とし、元互換出力と加工出力を混ぜない。採用時期が未記入のSVG／PNGはこの案により追加されない。

保存先を選ぶAPIは環境により利用範囲が異なるため、一つのAPIだけを必須にしない。[W8] 通常ダウンロード経路も設け、巨大出力時のメモリ、ブラウザ動作、途中失敗を実測する。研究データをサーバーへ渡してダウンロード用URLを作る方式は使わない。

### 12.2 セッションファイル

初期対象は、設定のみ、または設定＋結果の手動書き出し・再読込。元FASTA一式を同梱するデータセット移送は今回の対象にしない。

manifestにはschema version、engine／app版、RunSnapshot、結果索引、詳細アラインメントに必要な情報、入力の識別情報を入れる案。候補・メモをどこまで含めるかはレビューする。内部のOPFSパスやセッション所有トークンを移植先のファイル参照として使わない。

元FASTAを同梱しなくても、aligned sequence等の研究データは結果に含まれ得る。「配列なし」と説明しない。元の全長配列がない状態では、保存済みアラインメントを再表示できても、任意の周辺配列・全長抽出はできない。元ファイルを明示的に再選択し、内容・record対応を確認してから再接続する。

読み込みで検索を自動開始しない。旧結果を新エンジンで黙って再計算しない。スキーマ不一致・欠損・過大な長さ・不正な参照を検出する。入力名、HTML、スクリプト、外部URL、実行コードとして任意データを解釈しない。

### 12.3 レポート・コマンド

結果レポートは、検索を再実行せず結果を確認できる自己完結した形式を提案する。静的HTML等を使う場合は入力をエスケープし、外部スクリプト・外部画像・GA4を埋め込まない。静的レポートの生成と、公開サイトへアップロードする機能は別であり、後者は追加しない。

LOSAT CLI情報は現在のフォームでなくRunSnapshotから生成する。入力の除外、範囲指定、Combined／Separate、遺伝暗号表、前処理も再現できる手順にする。ブラウザで取得できない利用者の絶対ファイルパスは捏造せず、対応付けの説明を付ける。

R20の「初／保」は、直前の設問順にNCBI比較コマンド＝初、Methods生成＝保と読む仮整理を維持する。NCBI比較手順を単なるプログラム名置換で生成せず、固定した比較条件で検証する。対象シェルは担当案のレビュー事項。

## 13. 非送信とGA4を両立させる境界

### 13.1 約束すること

研究データは端末内で入力・検索・一時保存・表示・出力する。GA4採用を理由に、配列、ヘッダー、ファイル名、結果、メモ、入力断片をネットワークへ渡してよいとは扱わない。

「研究データを送信しない」と「ネットワーク要求が一切ない」は異なる。アプリ資産取得、GA4、将来採用を判断する任意の外部機能を分けて説明する。

### 13.2 推奨する計測配置

**GA4は採用するが、研究データを扱う文書へGoogleのスクリプトを直接読み込まない構成を第一候補にする。** 別originの計測専用文書にGA4を閉じ込め、承認した固定イベントだけを渡す設計案である。解析画面を隠す大きなランディングページを必須にする意図ではない。

単なるTypeScriptモジュール分離ではセキュリティ境界にならない。originの境界はscheme・host・portで定まり、別パスに置くだけでは別originにならない。[W9] 専用文書をiframe等で組み込む場合、CSP・COEP・sandbox・postMessageのorigin／source検証まで試験する。これはR30で承認する新たな実装提案であり、既に採用済みの配置ではない。

初期のイベント候補はapp訪問と公開build等の固定情報に限定する。ファイル容量、入力配列数、結果数、検索パラメーター、検索時間など研究作業から生じる値を自動で送る案に広げない。イベントの追加は定義表の変更とレビューを要する。

GA4の拡張計測には該当ダウンロードのファイル名・リンク文字列、検索語等を収集する項目がある。[W10] 動的URL・タイトル・リンク名へ研究データを混ぜず、拡張計測・自由形式dataLayer・自動エラー送信を無検討に有効化しない。

同意後にタグを読み込むBasic型の方式を推奨案とする。Advanced型では未同意でもcookieなしの計測が送られるため、cookie不使用と通信不発生を同一視しない。[W11] 同意方式・保存期間・計測指標は未確定であり、本書は法的適合性の判定を行わない。

GA4がブロック・未同意・オフラインでも、検索・結果・抽出・保存機能は通常どおり動くことを要求する。

### 13.3 配信・入力・通信試験

解析用JS・Wasm・フォント・例題は自分の静的資産として配る。研究データをURL、クエリ文字列、document.title、DOM属性を介した計測値、ログ送信へ入れない。入力ヘッダーをHTMLとして実行しない。診断ログはローカル出力を基本とし、アプリからの送信は保留のまま。

CSPは画面とWorkerの双方で検討する。Workerは文書とは別にCSP適用を考慮する必要がある。[W12] connect-srcを自originに限定しただけで、自サーバーへの研究データ送信が防げると判断しない。使用する全通信経路を列挙し、許可する資産取得と計測のpayloadを検査する。

固有の試験文字列を配列・ヘッダー・ファイル名・メモ・不正入力へ入れ、正常・取消・失敗・書き出し・再読込・更新・GA4経路を確認する。試験に通ったことをあらゆる未知の脅威への絶対保証とはせず、依存資産・配信設定・実装レビューと併せて検証根拠にする。

## 14. オフラインと明示更新

Service Workerはアプリ資産のキャッシュ専用とし、研究データはそこへ混ぜない。app JS、Wasm、Workerスクリプト、schema、能力表、検証情報、必要な例題を一つのReleaseManifestで結び付ける。

資産準備は、その版の必須機能をそろえる方針を推奨する。初回表示をすべてのコンパイル終了まで止めず、入力操作と準備を並行させる。必要な資産がそろった範囲だけ準備完了とし、五programの必須経路が未準備なのに全体をOffline readyとしない。

新規のオフライン起動まで初期の検証に含める案をレビューする。これは前回の研究データを復元することではなく、キャッシュされたアプリを空の作業として開くことを意味する。PWAのインストール案内等は後続のまま。

### 更新手順案

利用者が更新を選ぶ → 必要資産と整合性を確認 → 実行中・未保存作業への影響を案内 → 同意されたタイミングで新releaseへ切替、という流れにする。取得が不完全なら今のreleaseを維持する。

Service Workerは新バージョンの待機・有効化のライフサイクルを持ち、skipWaitingによって旧ページを新Workerが制御する状態が生じ得る。[W13] 無条件のskipWaitingや新旧Wasm混在に依存しない。

**「待機するService Worker」だけで、次回起動後も明示更新を守れるとは考えない。** 採用済みrelease IDを研究データとは別のアプリ設定として保持し、HTML／JS／Wasmをversion付き資産へ固定する案とする。SWがライフサイクル上更新されても、アプリreleaseを黙って切り替えない契約を設ける。新旧タブが並存する間、旧タブが必要とする資産を消さない。

旧版資産をどこまで配布・保守するかは未決であり、無期限の旧版利用保証はしない。特定版を供給できなくなった場合は、黙って最新へ切り替えるのではなく状態と選択肢を説明する。

## 15. 技術選択とコード境界の案

フロントエンドはTypeScriptの小さな静的SPAを基本案とする。具体フレームワークと配置は既存コードを確認して選ぶ。状態機械・型付きメッセージ契約・Worker・ブロックI/O・エクスポートの責務を、特定UIフレームワークへ強く結び付けない。

エンジンは既存LOSATの検索ロジックとformatterを再利用し、Web adapter、入力供給、取消・進捗、詳細取得の境界を追加する。既存CLIと他の利用先への互換性を維持する。全面書き直しはこの構想の承認範囲に含めない。

コード配置例は次のとおり。現行のディレクトリ構成を確認した結果ではない。

```text
web/
  ui/                検索・結果・抽出・候補
  application/       draft、run、queue、操作契約
  domain/            ID、座標、実行記録、選択
  runtime/           supervisor、worker protocol
  storage/           source、index、memory、OPFS、cleanup
  results/           summary、details、view query
  export/            formatter adapter、FASTA、report、session
  assets/            manifest、offline、update
  tests/             unit、integration、browser、privacy

engine側（既存構成に合わせて配置）
  Web adapter / SequenceProvider境界 / result event contract
  既存検索コア・formatter・CLI
```

SOLIDは、データ所有・検索・出力・表示を異なる責任として保つために適用する。KISSは、アクティブ検索を一つにし、必要な二つの作業ストアから始めることに適用する。DRYは、検索数値・座標変換・パラメーター解釈・出力formatterを重複実装しないことに適用する。YAGNIは、未採用の公開SDK・ネイティブ版・クラウド同期・汎用プラグイン基盤を先回りして作らないことに適用する。

## 16. 開発順序と検証成果物

段階は開発上の区切りであり、正式公開の範囲を縮める段階ではない。

| 段階 | 実施する内容 | 次段階へ進む証拠 |
|---|---|---|
| 0. 実装と比較条件の固定 | 対象commit・toolchain、program/task/output、既存ハンドル、詳細情報、並列化、NCBI参照画面を調査 | 要求対応表、欠落一覧、固定フィクスチャ |
| 1. 高リスク境界の試作 | 全五programの詳細取得契約、共有／非共有取消、Subject再利用、大容量ブロック処理の成立性 | 小さなE2Eとバイト比較、CPU・メモリ・停止時間の実測 |
| 2. 作業データ基盤 | Source／revision、索引、Memory／OPFS、一時データ所有とGC、結果staging | cache cold/warm、quota failure、強制終了、別タブ保護 |
| 3. 実用画面 | 検索／結果、キュー編集、候補、図、全詳細、初期抽出 | 代表的研究作業と境界条件のブラウザ試験 |
| 4. 出力と配信 | 互換出力、CSV／JSON、report／session、オフライン、明示更新、GA4隔離案 | 再読込、原配列再接続、ネット切断、漏出試験 |
| 5. 正式公開判定 | 五program、全初期機能、対応環境、入力規模、例題・説明を評価 | 受入表と既知例外、未達なしの公開判断 |

UIを完成させてから「コアが詳細を返せない」「巨大ファイルを全量ロードするしかない」「取消で結果が消える」と判明しないよう、最初に境界の試作を置く。

### 主な受入試験

| 試験 | 確認する性質 |
|---|---|
| 五program × outfmt 0/6/7 | 固定NCBI条件とのバイト比較。例外は限定・記録 |
| cold/warm・Memory/OPFS | 同じ入力・実効条件で結果を変えず、準備短縮と資源量を分けて測る |
| serial/threaded・batch size | 実行資源・I/O分割の都合でヒット・順位・統計を変えない |
| 複数query・入力順 | queryの完了順と出力順を混同せず、重複IDでも結果を取り違えない |
| Combined/Separate | 論理Subject集合と独立検索の意味を保持 |
| 巨大単一レコード | 境界、翻訳frame、正逆方向、延長の連続性 |
| 重複ID・入力更新 | 過去の結果・キュー・候補が新しい同名入力に付け替わらない |
| 取消と遅延イベント | CPUを止め、stagingを破棄し、旧世代の完了通知を拒否 |
| 停止後の作業 | Subject・以前の結果・候補・メモ・停止記録が残り、次の検索ができる |
| quota・I/O失敗 | 成功を装わず、元結果や前の作業を破壊しない |
| GC・複数タブ | 実行中／休止中／旧版タブ／出力中の保持物を誤削除しない |
| 抽出・座標 | 領域指定、端部、複数HSP、逆向き、翻訳で原配列と一致 |
| セッション再読込 | 再計算なしで結果を表示。元配列がない操作は明示。勝手な入力再接続なし |
| オフライン・更新 | 必須資産だけで一連操作。新旧混在なし。ユーザー未選択の版切替なし |
| privacy・GA4 | 正常／異常／出力／更新で研究データを送らず、計測がなくても検索可能 |
| モバイル実機 | 初期対象機能と資源・中断動作。デスクトップエミュレーションだけで代用しない |

速度・容量・応答時間の数値は実測後にレビューする。「大きいほどよい」「Wasmでできることはすべて」を、無限容量や全入力の線形スケーリング保証へ変換しない。

## 19. 結論

このアプリの設計単位は、検索コマンド一回ではなく、**「同じSubjectを使って複数回検索し、結果を確認し、必要な配列を回収する一つの作業」**である。

そのため、元データと作業状態を計算Workerから独立させ、部分読み出し可能な入力、条件付きの前処理再利用、上限付きメモリ、確認不要の一時ファイル、run単位の結果確定、元配列へ戻れる結果モデルを中心に置く。

同時に、五programと全詳細表示を初期要件として維持し、表示の都合で検索意味を変えない。研究データの自動復元を作らず、保存用ファイルは明示操作に限定する。GA4・更新・配信まで含めて非送信の境界を検証する。

**長く保持するのは利用者の今の作業、必要時に捨てられるのは計算の実体と再生成可能なキャッシュ、とするのが本構想の中心である。**

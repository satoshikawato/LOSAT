# LOSAT v0.2.0 certification plan: lineage, certification set, platform claims

Status: plan (2026-10-25, release line RL1; scope, counts and dispatch updated 2026-11-17, counted at
dev `bc9448188`). The results are written into `docs/release/v0.2.0.md` (the GO record) and the run
identifiers into `docs/release/v0.2.0_rc_contract.json` when the candidate is certified. Owner decisions
this plan rests on: v0.2.0 is cut from dev's head, so what merges before the candidate commit is in
(Owner, 2026-11-17; this replaces scope B' of 2026-10-25); from 2026-10-25: the cut waits until the
always-on switches have graduated, memory at or below NCBI on every cell of the standard table
(n <= 16) is required, no speed regression, five native platforms and WASI serial certified, WASI
threads supported, the Web GUI a preview, the TBLASTX local-subject genetic-code deviation kept as an
approved difference.

## 1. Lineage: what is re-run and what is reused

v0.1.0 certified the integrated runtime at `5845d22ed` (2026-08-31) and four native platforms at
`647e5f13c` / `e9f07039f` (2026-09-02 / 2026-10-14), and its release-candidate assembler reused that
certification only when the candidate differed from the certified commit in no runtime input
(`prepare_release_candidate_v010.py`, `RUNTIME_INPUT_PATHS`). `LOSAT/src` changed in more than 4,500
commits since; the reuse rule correctly refuses every v0.2.0 candidate. The v0.1.0 contract, assembler
and workflow stay as they are (frozen 0.1.0 records); v0.2.0 gets its own three files.

Rules for v0.2.0:

1. **Everything LOSAT-side is re-run on the candidate commit** `C` (the dev commit that is promoted to
   `main` on the cut day). `C` stays the dev commit: every GitHub run of the sets below is dispatched
   on a branch whose head is `C` (`cert/<first 9 hex of C>`, section 7). The promotion PR is merged as
   a merge commit `M` on `main` with `C`'s tree (`git diff --quiet C M` is empty, so `C` is an ancestor
   of `M`), and `release/0.2` is made at `M`. No LOSAT output hash, classification or platform result
   from an earlier commit is carried over as certification evidence. Historical hashes stay in the
   manifests as provenance only.
2. **Reused: NCBI-side records only.** The frozen NCBI BLAST+ 2.17.0 outputs
   (`LOSAT/tests/outfmt0_manifest.tsv`, `db_search_manifest/`, `*_regression`, `range_regression`,
   `fasta_input`, the Gate A manifests) and the NCBI platform characterisation
   `LOSAT/tests/ncbi_platform_variance_v011.json` (PD-NCBI-PLATFORM-VARIANCE) are records of NCBI's
   behaviour and do not depend on LOSAT's commit. The `-subject` fixture rows are nevertheless
   re-executed with the oracle on the certification day (set D below), which turns "frozen" into
   "executed" evidence for every program and task.
3. **The release-candidate commit `R` may differ from `C` only outside the runtime inputs.** `R` is
   `M` plus document-only commits on `release/0.2`. After the runs, the contract is filled (candidate
   SHA, run identifiers, evidence hashes) and committed with the release documents on `release/0.2`;
   that commit `R` is the one the RC workflow builds and tags. The
   assembler requires `C` to be an ancestor of `R` and `git diff --quiet C R -- <runtime inputs>` to be
   empty. Runtime inputs of v0.2.0: `LOSAT/src`, `LOSAT/Cargo.toml`, `LOSAT/Cargo.lock`,
   `LOSAT/build.rs`, `LOSAT/.cargo`, `LOSAT/tests` (fixtures, manifests, gate scripts) except the two
   release-tooling files `LOSAT/tests/prepare_release_candidate_v020.py` and its test, and
   `docs/product_decisions`. `README.md`, `LICENSE`, `CHANGELOG.md`, `docs/release`, `changelog.d` and
   the Bioconda recipe may change between `C` and `R` (they go into the archives as documents).
4. A fix found by the certification produces a new candidate `C'`; every run of section 2 is repeated
   on `C'` (the GitHub side is about one working day in wall time, the local side a few hours).
5. Lineage of v0.2.0 towards v0.1.0 is recorded, not relied upon: the contract keeps the v0.1.0
   certified SHAs and the assembler checks that `C` descends from them (provenance of the oracle set).

### 2.1 Threaded Wasm out-of-bounds traps (closed)

The nightly of 2026-10-25 failed once on a branch run with `memory access out of bounds` in
`__wasi_thread_start_C` (blastx, 16 threads) and passed on rerun; the Owner held GO until the cause
was known. Its cause, a thread worker that started with a stale memory length, was fixed in the
Node host by `memory.grow(0)` before `wasi_thread_start` (#513,
`docs/evidence/wasm_oob_20261025/README.md`). A second, rare trap (1 of 483 runs, 2026-11-01) was an
atomic instruction against a stale memory bound; #703 fixed it, and after the clearing runs
(`docs/evidence/wasm_oob_20261101/README.md`, "After merge") the Owner lifted the GO item on
2026-11-02. Set G still runs three times in a row on `C`.

- **Hash equality across the five platforms**: `platform_check_cases.json` has 59 cases. Pull request

## 7. Order of the runs on the cut day

1. `C` = head of dev with green PR CI and green nightly; the always-on switch graduation PRs and the
   pre-cut document PRs merged. `promote/<date>` PR to `main` (platform-checks run there); merge as a
   merge commit `M` (not a squash); `git diff --quiet C M` must be empty, and its result is recorded in
   the GO record; `release/0.2` at `M` (Owner).
2. Dispatch in parallel (the session). Every dispatch runs on a branch whose head is `C`:
   `git push origin <C>:refs/heads/cert/<first 9 hex of C>`, then `gh workflow run <file> --repo
   satoshikawato/LOSAT --ref cert/<9 hex>` with `platform-native-certification.yml -f candidate_sha=C`,

## 8. Not provided in v0.2.0

What v0.2.0 does not provide on dev, as README.md lists it ("Scope & Differences from NCBI BLAST+"):

- On the Owner's next-release list (2026-11-17): `deltablast`, `makeprofiledb`, `psiblast -phi_pattern` beyond its first round,
  with `-html`, or with output formats other than `0`, `6`, `7`, `10` and `20`, the `psiblast` output formats `13` to `16`,
  the `blast_formatter` output formats other than `8`, `9` and `12` and its archives in ASN.1 binary or XML, and `windowmasker`.
- Programs not provided: `blast_formatter_vdb`, `blast_vdb_cmd`, `blastn_vdb`, `tblastn_vdb`,
  `legacy_blast.pl`, `update_blastdb.pl`, `get_species_taxids.sh`, `cleanup-blastdb-volumes.py`.
- Out of scope (they need NCBI's servers): `-remote` and `-entrez_query` (all programs).
- `-import_search_strategy` in `psiblast`, `rpsblast` and `rpstblastn`, and strategy files in binary
  or XML form (it runs text strategy files in `blastn`, `blastp`, `blastx`, `tblastn` and `tblastx`).
- The Web GUI's search results (preview).
- Any configuration with a `LOSAT_X_*` variable set.

The threaded Wasm binary is supported with no NCBI parity claim (section 6).

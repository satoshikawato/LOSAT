# Session S15 — W6：出力と再現性

## INSTRUCTION PROMPT

LOSAT Web の段階 W6 を実行する。先に [セッション README](README.md) の共通規則を読み、それに従う。完了条件の正本は、総合計画書 §7 の S15 の行である。設計は計画 §5.8、設計書 §12 にある。

始める前に、セッションファイルに候補とメモを含めるかを保守者に確認する（計画 §10）。

1. 互換出力：outfmt 0/6/7 の書き出しは S01 で作ってある。保存したテキストを 1 バイトも変えずに出し、範囲は実行の結果全体だけにする。
2. アプリ独自の出力：CSV・JSON（HSP レコードから作り、ViewState のフィルターや選択を反映できる）、結果レポート（外部スクリプトも計測も含まない静的 HTML、入力はすべてエスケープ）。どれも LOSAT Web の形式であると明記し、NCBI と一致するというラベルを付けない。書き出しは、メモリへ全体を組み立てずに、ブロックを順に書く。
3. 設定ファイル：検索条件（program、入力名を除いた argv、スレッドの設定）だけを書き出し、読み込むとフォームに入る。
4. セッションファイル：manifest（schema の版、app / engine の版、RunSnapshot、レコード表、入力の SHA-256）と、テキスト・レコードのブロックを長さ付きで並べた単純なコンテナにし、`CompressionStream` で gzip する。読み込んでも検索は始めない。スキーマの不一致、欠け、長すぎる値、不正な参照を検出して拒否する。入力の名前や内容を HTML・スクリプト・URL として解釈しない。flank や全長の抽出には元の FASTA を選び直してもらい、SHA-256 が一致したときだけつなぎ直す。内部の OPFS のパスやセッションのトークンは書き出さない。
5. 再現の手順：CLI コマンドと、NCBI との比較用のコマンドを RunSnapshot の argv から作る。既定以外の subject の遺伝暗号を使う TBLASTX / TBLASTN では、承認済みの例外であることを注記する。レコードを除外した実行やファイルをつないだ実行では、「この実行に使った入力 FASTA」を書き出せるようにする。
6. 試験：セッションを再読込しても再計算しないこと、元配列が無いとできない操作が明示されること、勝手につなぎ直さないこと、壊れたセッションファイルを拒否すること。

完了条件は計画 §7 の S15 の行による。記録は `docs/evidence/losat_web_w6/README.md`。

## S14（W5）から引き継ぐこと

[W5 のゲート記録](../evidence/losat_web_w5/README.md)の要点。上の 1.〜6. の条件はこの節で緩めない。

- **候補トレイと研究データ**：トレイ（`src/application/candidates.ts` の `CandidateTray`）は app の状態だけで、保存も送信も URL への記載もしない。候補（元の結果への参照 `HspId` = `runId`・`qIdx`・`rank`、`index`、Run の要約、query / subject のレコードの位置・ID・長さ・単位、座標、outfmt 6 の行）とメモは研究データである。計画 §5.8 のとおり、セッションファイルに含めるかは保守者が S15 の前に決める（上の「始める前に」）。含めるなら、候補が指す Run がセッションに入っていなければ「元の結果へ戻る」と抽出は成り立たない（REQ-10：登録・抽出・書き出しは完了した Run だけ。アプリ層で拒否する）。`origins()` は Run ごとの由来（program、argv の `slice(5)`、query / subject の名前と SHA-256、build、終了時刻、候補の数）を返す。この SHA-256 は `InputSnapshot.sha256`、つまりエンジンに渡した入力の byte（含めたレコードをつないだもの）で、元の file の SHA-256 とは限らない（下の「reader の kind」）。
- **抽出の形式は LOSAT Web の形式**（NCBI の形式ではない）：配列の header は `>{id}:{from}-{to} run={N} {role}_record={K} length={L} unit={nt|aa} hsps={Q.R,...} hit_strand={...}[ requested={a}-{b}]`、整列の header は `>{id}:{start}-{end} run={N} {role}_record={K} hsp={Q.R} aligned[ frame={f}]`（start > end のまま）。1 行 60 文字、LF。空の ID は `Query_K` / `Subject_K`（outfmt 6 の名前）、`length=` はレコードの長さ、`K` は 1 始まりのレコードの位置（重複 ID を区別する）。file 名は `losat-candidates.fa` と `losat-candidates-aligned.fa`（`text/plain`、入力の名前を使わない）。S15 の CSV・JSON・レポートや書き出しの画面でこれらを扱うときは、LOSAT Web の形式と明記し、NCBI と一致するというラベルを付けない。実装は `src/domain/extraction.ts`（`sequenceHeader`、`alignmentHeaders`、`fastaRecord`、`FASTA_LINE_WIDTH`）。
- **Data worker の読み**（`src/ports/data.ts`）：`readResidues(revisionIds, position, intervals)` は、Run の入力の `position` 番目のレコードの原配列を元の File から読む（大文字小文字と `U` はそのまま、行末・空白・コメントは除く。区間ごとに 1 つの `Uint8Array`。区間の byte だけを読む）。`readHspRecords(runId, indices)` は HSP レコード（整列文字列を含む）を index の順で返す。コードの上では、整列の書き出し（`exportAlignments`）は保存した Run の出力だけで足りるので元の FASTA が無くてもできるが、配列の抽出（ヒット区間・flank・全長のどれも）は元の File を読むので、セッションを読み込んだだけではできない。この区別を S15 の「元配列が無いとできない操作を明示する」に使える。
- **reader の kind と原 FASTA のつなぎ直し（REQ-23）**：S14 で索引の scan を kind 1（核酸）・2（タンパク質）に替えた。kind は program と役割で決まる（`indexParser(program, role)`、BLASTX は query が 1・subject が 2）。レコード表（`DatasetRevision.records`、byte の offset、`line_layout`、`residue_counts`）はその kind で読んだときだけ正しい（`DatasetRevision.parser` が持つ）。プログラムを替えて役割の kind が変わると索引し直し、その役割の除外は消える（W5 の判断 13、画面レビュー 2 回目の参考 I2）。つなぎ直しは、(1) 選び直した file を、manifest が記録した kind で索引し直し、(2) レコード表（ID、長さ、レコードごとの SHA-256 = `DatasetRecord.sha256`、defline の無い最初のレコードの offset 0/0）が一致するときだけ受ける、という形になる。`InputSnapshot.sha256` はレコードを除外した実行やファイルをつないだ実行では元の file の SHA-256 と一致しないので、manifest にはレコードごとの SHA-256 と kind も持たせる必要がある。`readResidues` は読んだレコードの ID・長さ・残基の数を表と照らし、食い違えば「no longer matches its record table … Add the file again.」で拒む。位置（`{role}_record=K`）と除外した index は表に依存する。
- **Writer の契約**（設計書 §12.1）：S14 の抽出は Writer を使っていない。`CandidateTray.extract` は断片ごとに `fastaRecord` で文字列を作り、`concat` で 1 つの `Uint8Array` にして `downloader.save(name, bytes, mime)` に渡す。コードレビュー L1：「Complete sequence」の抽出は、worker の読み（`count` byte）、`fastaRecord` の写し、`concat` の写し、Blob と、レコードの写しを 3〜4 つ持つ（250 Mbp で約 0.75〜1 GB）。2,147,483,647 文字に近いレコードは `new Uint8Array(count)` が失敗して抽出できない（「could not be extracted」）。読みそのものは区間で限っている（8 MiB 以下の slice）が、メモリに全体を組み立てないとは言えない。S15 は Writer の契約（抽出・formatter・serialize が共通の Writer にブロックを順に書く）を作り、抽出もそれに載せる。`ForwardReader` は chunk の境界をまたいで状態を保つので、streaming の読みの土台にできる。上の 2. の「メモリへ全体を組み立てずに、ブロックを順に書く」は抽出の書き出しにも当たる。
